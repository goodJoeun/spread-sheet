# 과제 설명 스크립트

코드를 화면에 띄워 놓고, 개발한 순서대로 설명하는 스크립트입니다.

<br>

## 이렇게 쓰세요

- 코드의 `[흐름 N]` 주석 번호 순서대로 진행합니다. VS Code에서 `Ctrl+Shift+F`로 `[흐름 `을 검색해 두면 바로 이동할 수 있습니다.
- 장면마다 세 가지 표시가 있습니다.
  - 📂 열 파일
  - 🗣 왜 이렇게 만들었는지. 그대로 읽어도 되도록 썼습니다.
  - 🧩 이 모듈이 맡은 일. 함수 이름과 역할을 짚습니다. 시간이 없으면 줄이고, 질문을 받으면 이 부분으로 답합니다.
- 🔁 표시가 붙은 장면은 기능 하나가 여러 모듈을 지나는 과정을 따라갑니다. 모듈 설명을 한 번에 묶어 주는 장면이라 되도록 빼지 마세요.
- 전체 약 25분 분량입니다. ⏩ 장면과 🧩 부분을 줄이면 약 15분입니다.

## 0. 시작 (1분)

🗣 여러 사람이 동시에 편집하고, AI에게 셀 편집을 맡길 수 있는 웹 스프레드시트를 만들었습니다. 서버 없이 같은 브라우저의 탭끼리 동기화하고, 내용은 브라우저의 IndexedDB에 저장합니다. 서버는 AI 호출에만 씁니다.

🗣 오늘은 화면보다 코드를 중심으로, 제가 개발한 순서대로 설명드리겠습니다. 코드에 `[흐름]` 번호를 붙여 두었는데, 이 번호가 커밋 순서입니다. 각 지점에서 무엇을 고민했고, 왜 이 구조로 정했는지를 말씀드리겠습니다.

🗣 먼저 전체 구조를 한 줄로 말씀드리면, import는 `app → components → hooks → lib` 한 방향으로만 흐르고, 로직이 모인 `lib`에는 React가 없습니다. `lib`은 다시 시트 자체(`sheet`), 탭 사이 동기화(`collab`), 시트 명령(`controller`), AI(`ai`)로 나뉩니다.

🗣 데이터는 두 갈래로 흐릅니다. 확정된 셀 값과 서식은 문서(Y.Doc)에 담겨서 저장되고 실행 취소 대상이 됩니다. 이름, 커서, 입력 중인 글자, AI 작업 상태는 참여 상태(awareness)에 담겨서 탭끼리 공유만 하고 저장하지 않습니다. "확정되지 않은 것은 문서에 넣지 않는다"가 이 앱 전체를 관통하는 원칙입니다.

🗣 구조를 정한 원칙은 세 가지입니다. 되돌리기 어려운 것부터 정했고, 규칙은 한 곳에만 두었고, 기준을 먼저 글로 쓴 뒤 코드를 거기에 맞췄습니다. 이 세 가지가 어떻게 나타나는지 따라가 보겠습니다.

## 1. 데이터 계층을 먼저 만들었습니다 (5분)

### 흐름 1 — 셀 주소 (`address.ts`)

📂 `src/lib/sheet/address.ts` 맨 위

🗣 첫 코드는 셀 주소 모듈입니다. 모든 모듈이 셀 주소를 쓰기 때문에, 아무것도 import하지 않는 가장 아래 모듈부터 만들었습니다. 순수 함수만 있어서 서버 코드(프롬프트, 가짜 API)에서도 그대로 씁니다.

🗣 주소는 두 가지 모양으로 다룹니다. "B2" 같은 A1 표기는 사람이 읽는 모양이라 문서의 키, AI와의 통신, 화면 표시에 쓰고, `{ row, col }` 좌표는 선택, 이동, 위치 계산에 씁니다. 행은 A1 표기에서 1부터, 좌표에서 0부터 세는데, 이 차이는 변환 함수만 압니다.

🧩 이 파일이 맡은 일은 네 묶음입니다.

- **열 번호 ↔ 열 이름**: `colToLabel`은 0을 "A", 26을 "AA"로 바꿉니다. 엑셀 열 이름에는 0에 해당하는 글자가 없어서 일반 26진법과 다르게 계산합니다. `labelToCol`은 그 반대입니다.
- **셀 하나**: `toA1`, `parseA1`. `parseA1`은 사용자나 AI가 쓴 주소가 들어오는 입구라서, 앞뒤 공백, 소문자, `$B$2` 같은 절대참조 표기까지 받아 주고, 형식이 틀리면 null을 돌려줍니다.
- **범위**: `normalizeRange`는 두 꼭짓점을 어떤 순서로 받아도 왼쪽 위·오른쪽 아래로 정리합니다. 아래에서 위로 드래그한 경우에 필요합니다. `rangeToA1`은 셀 하나면 "B2", 아니면 "A1:C3"으로 씁니다.
- **범위 계산**: `rangeContains`(셀이 범위 안인지), `boundingRange`(여러 셀을 감싸는 가장 작은 사각형, AI가 바꾼 셀들의 전체 영역에 씀), `forEachCell`(범위 안 셀을 행 순서로 돌기), `intersectRanges`(두 범위가 겹치는 부분, 잠금 범위 판정에 씀).

### 흐름 2 — 평평한 키 (`document.ts`)

📂 `src/lib/sheet/document.ts` 15번째 줄 근처

🗣 그다음은 그리드가 아니라 데이터 모양이었습니다. 공동 편집에서 가장 바꾸기 어려운 결정이 저장 형식이기 때문입니다. 화면은 나중에 바꿀 수 있지만, 저장 형식을 바꾸면 저장된 데이터와 다른 탭의 코드가 모두 영향을 받습니다.

🗣 처음 떠오른 모양은 셀마다 Map을 하나씩 두는 것이었습니다. 그런데 빈 셀에 한 사람이 값을 넣는 순간 다른 사람이 굵게를 누르면, 두 탭이 각자 그 셀의 Map을 새로 만들고 한쪽이 통째로 사라집니다. 그래서 평평한 키로 저장했습니다. 서로 다른 키라서 동시에 바뀌어도 둘 다 남습니다.

```
Y.Doc
├─ "values"  (Y.Map<string>)          "B2" → "100", "C3" → "합계"
└─ "formats" (Y.Map<true | string>)   "B2.bold" → true, "B2.color" → "#ff0000", "C3.align" → "center"
```

🗣 값과 서식을 다른 Map에 둔 것도 같은 결정입니다. Delete로 값만 지우거나 AI에 보낼 셀 목록을 만들 때 서식을 걸러낼 필요가 없습니다.

🧩 셀을 읽고 쓰는 코드는 모두 이 파일을 지납니다.

- **읽기**: `getValue`는 키가 없으면 undefined 대신 빈 문자열을 돌려줍니다. `getFormat`은 "B2.bold", "B2.color"처럼 흩어진 키를 모아 서식 객체 하나로 묶습니다.
- **값 쓰기**: `writeValues`가 중심입니다. 여러 셀을 한 트랜잭션으로 쓰는데, 이미 같은 값인 셀은 건너뛰고, 빈 문자열이면 키를 지우고, 시트 밖 좌표는 무시하고, 실제로 바뀐 셀 수를 돌려줍니다. 같은 값을 건너뛰기 때문에 실행 취소 기록에 아무것도 안 바뀐 단계가 생기지 않습니다. `setValue`(셀 하나)와 `clearValues`(범위의 값만 지우고 서식은 둠, 엑셀의 Delete와 같음)는 이 함수를 부릅니다.
- **서식 쓰기**: `toggleFormat`은 범위 전체에 켜져 있으면 끄고, 하나라도 꺼져 있으면 모두 켭니다(구글 시트와 같음). `setStyle`은 색·정렬처럼 값을 갖는 서식을, `commonStyle`은 범위 전체가 같은 값인지(툴바 표시용)를, `clearFormats`는 서식만 지웁니다.

### 흐름 3 — 변경의 출처 (`EditOrigin`, `undo.ts`)

📂 같은 파일, `EditOrigin`

🗣 모든 변경에는 출처를 붙입니다. 사람이 고치면 `user-edit`, AI 결과를 적용하면 `ai-apply`입니다. 실행 취소는 이 두 출처만 추적합니다. 다른 탭에서 온 변경은 출처가 다르기 때문에, 제 Ctrl+Z가 다른 사람의 입력을 지우지 않습니다.

🗣 여기서 말씀드리고 싶은 점은, 이 `Ai` 출처를 AI 기능을 만들기 하루 전에 이미 넣어 두었다는 것입니다. 실행 취소 기준은 나중에 바꾸기 어려워서, AI 결과가 들어올 자리를 처음부터 만들어 두었습니다. 덕분에 AI 결과는 한 트랜잭션으로 쓰기만 하면 실행 취소 한 번으로 모두 되돌아갑니다.

🧩 `src/lib/collab/undo.ts`의 `createUndoManager`가 이 설정을 담고 있습니다. 추적하는 출처는 두 개(`trackedOrigins`)이고, `captureTimeout`을 0으로 두었습니다. Yjs 기본값은 0.5초 안에 이어진 편집을 한 단계로 합치는데, 스프레드시트에서는 "동작 하나 = 실행 취소 한 단계"가 자연스럽다고 판단했습니다.

### 흐름 4 — 탭 간 전송 (`broadcast-provider.ts`)

📂 `src/lib/collab/broadcast-provider.ts` 맨 위

🗣 조건이 "서버 없이 브라우저 API만"이었기 때문에, BroadcastChannel로 탭끼리 통신하는 provider를 직접 만들었습니다. 다만 메시지 형식은 y-websocket과 똑같이 맞췄습니다. 나중에 서버로 넓힐 때 이 클래스만 WebsocketProvider로 바꾸면 되게 하기 위해서입니다.

🧩 provider는 탭마다 하나씩 있고, 탭들이 공유하는 것은 `spread-sheet:시트ID`라는 이름의 채널 하나입니다. 채널에 메시지를 올리면 같은 채널을 연 다른 탭이 모두 받습니다. 탭마다 문서 복사본이 따로 있고, 메시지를 주고받으며 복사본들을 같게 맞추는 구조입니다.

🗣 (`announce` 메서드를 가리키며) 새 탭이 열리면 두 단계로 알립니다. Step1은 "나는 어느 탭의 변경을 몇 개까지 갖고 있다"는 목록(상태 벡터)이고, Step2는 실제 변경 내용입니다. 메시지 번호는 두 겹입니다. 바깥 번호는 종류(0: 문서 동기화, 1: 참여 상태, 3: 참여 상태 요청)이고, 문서 동기화 안쪽 번호가 Step1(0)인지 Step2(1)인지를 나타냅니다. y-websocket과 같은 번호입니다.

🗣 한 번 보내면 모든 탭이 받는 구조라서 두 가지를 정했습니다. 다른 탭에서 받은 변경은 다시 방송하지 않습니다(`handleDocUpdate`의 `origin === this`). 다시 보내면 탭끼리 같은 변경을 끝없이 주고받습니다. 그리고 참여 상태는 자기 것만 보냅니다. 남의 상태를 대신 보내면 이미 떠난 사용자가 되살아나 목록이 깜빡입니다.

🧩 `resync()`는 뒤로/앞으로 가기 캐시(bfcache)에서 복원된 탭이 멈춰 있던 동안 놓친 변경을, 합류할 때와 같은 절차로 다시 받을 때 씁니다. 이 파일은 전달만 맡고, 편집 규칙이나 화면은 모릅니다.

### 흐름 5 — 조립 지점 (`session.ts`) ⏩

📂 `src/lib/collab/session.ts`, `createSheetSession`

🗣 문서와 부품들은 이 함수 한 곳에서 조립합니다. 문서와 화면은 저장·전송 방식을 모르기 때문에, 방식을 바꿀 때 고칠 곳이 이 함수로 모입니다.

🧩 시트 하나에 부품 여섯 개를 만들어 잇습니다. 셀 값과 서식을 담는 `Y.Doc`, 저장하지 않는 상태를 담는 `Awareness`, 저장을 맡는 `IndexeddbPersistence`, 다른 탭과 동기화하는 `BroadcastChannelProvider`, 참여자 목록을 만드는 `Presence`, 실행 취소를 맡는 `UndoManager`입니다. `leave()`, `rejoin()`, `destroy()`로 탭을 떠날 때, bfcache에서 돌아올 때, 정리할 때를 처리합니다. 협업 모듈들의 수명을 관리하는 진입점입니다.

## 2. 그리드와 한글 입력 (2분)

### 흐름 6 — 작은 저장소 (`store.ts`)

📂 `src/lib/store.ts`

🗣 그리드를 만들면서 상태 관리 라이브러리를 쓸지 고민했습니다. 키를 누르는 순간에는 화면이 다시 그려지기를 기다리지 않고 최신 선택 위치를 바로 읽어야 하는데, React state만 쓰면 이전 값을 읽을 수 있습니다. 필요한 건 읽기, 바꾸기, 알리기 세 가지뿐이라 24줄짜리 저장소를 직접 만들고, 화면은 React 표준 방식(`useSyncExternalStore`)으로 구독만 하게 했습니다.

### 흐름 7 — 한글 입력 (`useCellEditor.ts`, `keymap.ts`)

📂 `src/hooks/grid/useCellEditor.ts` 맨 위

🗣 그리드에서 가장 오래 고민한 곳이 한글 입력입니다. 셀을 고르고 바로 타이핑하는 순간 포커스를 편집칸으로 옮기면, 한글 조합이 끊기고 첫 자모가 사라집니다.

🗣 그래서 투명한 편집칸이 항상 선택한 셀 위에서 포커스를 쥐고 있게 했습니다. 그리고 편집칸의 값은 React가 관리하지 않습니다. React가 다시 그리면서 값을 덮어쓰면 조합 중인 글자가 깨지기 때문입니다. 조합 중에 누른 Enter도 시트가 처리하지 않습니다. 셀 이동으로 처리하면 마지막 글자가 사라지거나 두 번 들어갑니다.

🧩 키 해석은 `src/lib/sheet/keymap.ts`의 `resolveGridKey`가 맡습니다. 키를 받아 "무슨 동작인지"만 돌려주고, 실행은 컨트롤러가 합니다. 같은 키라도 편집 모드에 따라 다르게 해석합니다. 셀을 고르고 바로 타이핑한 enter 모드에서는 방향키가 입력을 확정하고 셀을 옮기고, F2나 더블클릭으로 시작한 edit 모드에서는 글자 사이 커서를 움직입니다. 단축키 정의와 툴바에 보여 줄 단축키 표기(`shortcutLabel`)도 이 파일 한 곳에서 관리합니다.

### 흐름 8 — 셀 값을 복사하지 않습니다 (`useDocVersion.ts`) ⏩

📂 `src/hooks/sheet/useDocVersion.ts`

🗣 화면은 셀 값을 따로 복사해 두지 않습니다. 문서가 바뀌었다는 신호로 숫자 하나만 받고, 그릴 때마다 문서에서 직접 읽습니다. 원본이 하나뿐이라 원본과 복사본이 어긋날 일이 없습니다.

### 흐름 9 — 서식 두 종류 (`schema.ts`) ⏩

📂 `src/lib/sheet/schema.ts`, `FORMAT_KEYS`

🗣 서식은 굵게처럼 켜고 끄는 것과, 글자색처럼 값을 갖는 것으로 나눴습니다. 값 서식은 다른 탭이나 AI에서 온 값도 같은 검증 함수(`isValidStyle`)를 거칩니다.

## 3. 참여자 표시와 로직 분리 (5분)

### 흐름 10 — 탭이 닫힌 걸 어떻게 아는가 (`liveness.ts`)

📂 `src/lib/collab/liveness.ts`

🗣 처음 계획은 타이머 방식이었습니다. 각 탭이 15초마다 "살아 있다"고 알리고, 30초 동안 소식이 없으면 지우는 방식입니다. 그런데 크롬은 가려진 탭의 타이머를 늦춥니다. 그래서 열려 있는 탭이 목록에서 사라졌다 나타났습니다.

🧩 그래서 `TabLiveness`가 Web Locks로 탭 종료를 감지합니다.

1. 각 탭이 자기 번호(clientID) 이름의 잠금을 쥡니다.
2. 다른 탭은 그 잠금을 얻을 때까지 기다립니다.
3. 탭이 닫혀 잠금이 풀리면, 기다리던 탭에 잠금이 넘어옵니다.
4. 그 순간 콜백으로 그 사용자의 참여 상태를 지웁니다.

🗣 타이머 없이 즉시, 정확하게 알 수 있습니다. Web Locks를 쓸 수 없는 환경에서는 기본 타이머 방식으로 돌아갑니다.

### 🔁 흐름 따라가기 ① — B2에 100을 입력하고 Enter를 누르면

🗣 여기까지 나온 모듈들이 실제로 어떻게 맞물리는지, 셀 하나를 고치는 과정으로 보여 드리겠습니다.

```
 탭 A                                              탭 B
 ① 타이핑 시작   startEdit()          ──참여 상태──▶  "B2 입력 중" 표시
 ② 입력 중       draftChanged()       ──참여 상태──▶  B2 위에 "10…" 미리 표시
                 (문서는 그대로)
 ③ Enter         commitEdit() → setValue → transact(origin = "user-edit")
 ④ 문서 update ┬ provider: 채널로 방송 ─────────▶  ⑤ 받아서 문서에 적용
               ├ IndexedDB: 저장                       (origin = provider)
               ├ UndoManager: 실행 취소 기록            → 다시 방송하지 않음
               └ 화면: 다시 그림                        → 실행 취소 기록 안 함
```

🗣 ① 편집을 시작할 때 컨트롤러는 먼저 다른 사람이 이 셀을 잠갔는지 확인합니다. ② 글자를 칠 때마다 입력 중인 글자를 참여 상태로 보냅니다. 문서는 아직 바뀌지 않습니다. ③ Enter를 누르면 그제야 `"user-edit"` 출처를 붙여 문서에 씁니다.

🗣 ④ 문서가 바뀌면 네 곳이 각자 듣습니다. provider는 출처가 자기가 아니니 방송하고, IndexedDB는 저장하고, UndoManager는 출처가 `user-edit`라서 기록하고, 화면은 다시 그립니다. ⑤ 탭 B는 받은 변경을 문서에 적용하는데, 이때 출처가 탭 B의 provider입니다. 그래서 다시 방송하지 않고, 실행 취소 기록에도 넣지 않습니다. 남이 한 변경을 제가 되돌리면 안 되기 때문입니다. 흐름 2~4에서 정한 것들이 여기서 한 번에 맞물립니다.

## 4. AI 편집 (6분)

### 흐름 18 — 서버 → 상태 관리 → 화면 순서 (`protocol.ts`)

📂 `src/lib/ai/protocol.ts` 맨 위

🗣 AI는 서버, 브라우저의 상태 관리, 화면 순서로 만들었습니다. 상태 흐름을 먼저 테스트로 굳혀 두면, 화면은 그 상태를 그리기만 하면 되기 때문입니다.

🧩 `lib/ai`는 AI 요청 한 번의 생명주기를 맡습니다. 전체 흐름은 이렇습니다.

1. `ai-controller.ts`가 현재 시트, 대화, 편집 범위를 모아 실행을 시작합니다.
2. `request.ts`가 요청 데이터를 만들고, `transport.ts`가 `/api/ai/edit`로 보냅니다.
3. 서버의 `validate.ts`가 요청을 검사하고, `setup.ts`와 `prompt.ts`가 Claude 호출을 준비합니다.
4. `claude.ts`가 글과 셀 제안을 스트리밍하고, `edit-stream-parser.ts`가 완성된 제안을 하나씩 꺼냅니다.
5. 브라우저의 `run.ts`가 실행 상태를 갱신하고, `coedit.ts`가 다른 사람의 변경과 충돌하는지 판단합니다.
6. 사용자가 적용하면 `ai-controller.ts`가 적용할 수 있는 제안만 한 트랜잭션으로 씁니다.

🗣 서버는 API 키를 브라우저에 보내지 않기 위해서만 있습니다. 서버 파일은 신뢰할 수 없는 데이터가 들어오는 경계마다 하나씩 나눴습니다. 브라우저 입력은 `validate`, 모델 출력은 `edit-stream-parser`, 환경 변수는 `setup`이 맡습니다. 서버 전용 파일에는 `import "server-only"`를 붙여서, 브라우저 코드가 가져가면 빌드가 실패합니다.

🧩 이 `protocol.ts`는 브라우저와 서버가 함께 보는 약속입니다. 요청 형식과 크기 제한, 고를 수 있는 모델, 오류·경고 형식, 스트림 이벤트를 정의합니다. 이벤트는 여섯 종류입니다. `meta`(실제 모델 정보), `text`(AI의 설명 글 조각), `edit`(셀 하나의 제안), `warning`(쓸 수는 있지만 알려야 할 일), `done`, `error`입니다. 브라우저는 받은 이벤트를 `parseStreamEvent`로 한 번 더 검사합니다. TypeScript 타입은 실제로 들어온 데이터까지 보장하지 않기 때문입니다.

🧩 주고받는 부품도 짚어 보겠습니다.

- **`request.ts`**: `snapshotCells`는 비어 있지 않은 셀만, 행 순서로, 개수와 길이를 제한해서 담습니다. 서식은 담지 않습니다. `conversationHistory`는 이전 대화를 글만 남겨 담습니다.
- **`transport.ts`**: 응답은 한 줄에 이벤트 하나인 NDJSON입니다. 데이터는 아무 데서나 잘려 도착할 수 있어서, `createLineSplitter`가 줄바꿈이 아직 안 나온 조각을 보관하고 완성된 줄만 넘깁니다. 네트워크 실패, HTTP 오류, 도중에 끊긴 연결은 모두 같은 오류 형식으로 바꿉니다. 사용자가 취소하면 브라우저의 요청과 서버의 모델 호출까지 함께 끊깁니다.
- **`validate.ts`**: zod로 지시문 길이, 셀 주소가 시트 안의 정규 A1 표기인지, 셀 개수와 값 길이, 대화 역할, 모델 id 길이를 검사합니다.
- **`prompt.ts`**: 시트는 `B2 = "1,000"`처럼 값을 JSON 문자열로 적어 보냅니다. 값에 줄바꿈이나 따옴표가 있어도 셀 경계가 섞이지 않습니다. 편집 범위를 함께 알려 범위 밖을 바꾸지 말라고 지시하고, 계속 바뀌는 시트 내용은 마지막 요청에만 넣습니다.
- **`claude.ts`**: SDK 이벤트를 앱 이벤트로 번역합니다. 최대 길이에서 잘리면 `truncated` 경고, 형식이 틀린 제안은 `invalid_edits` 경고로 바꾸고, SDK 오류(인증, 한도, 과부하, 거절 등)는 앱의 오류 코드로 바꿉니다.

🗣 오류를 알리는 방법도 고민했습니다. 응답을 보내기 시작하면 HTTP 상태 코드를 바꿀 수 없습니다. 그래서 `route.ts`는 첫 이벤트를 받은 뒤에 응답을 시작합니다. 키 오류나 요청 한도처럼 시작 전에 실패하면 HTTP 상태로, 시작한 뒤에 실패하면 스트림 안의 `error` 이벤트로 알립니다.

### 흐름 19 — 덜 만들어진 값은 받지 않습니다 (`edit-stream-parser.ts`)

📂 `src/lib/ai/server/edit-stream-parser.ts`

🗣 AI 결과는 글에서 찾아내지 않고, 도구 호출로 `{ cell, value }` 목록을 받습니다. 형식이 확실하고, AI의 설명과 실제 편집이 나뉩니다. 그런데 스트리밍으로 받다 보면 SDK가 "1250" 대신 "12"처럼 덜 만들어진 값을 넘길 수 있습니다.

🧩 그래서 이 파서를 직접 만들었습니다. 지금 문자열 안인지, 이스케이프된 문자인지, 어떤 괄호가 열려 있는지를 추적하다가, `edits` 배열 안의 객체 하나가 완전히 닫혔을 때만 `JSON.parse`를 실행합니다. 꺼낸 값은 셀 주소를 대문자로 정리하고, 모델이 숫자로 보낸 값은 문자열로 바꾸고, 길이를 제한합니다. 형식이 틀린 원소는 개수만 세어 경고로 알립니다.

### 흐름 20 — 가짜 API (`setup.ts`, `mock-anthropic.ts`) ⏩

📂 `src/lib/ai/server/setup.ts`

🗣 키 없이도 테스트할 수 있도록 가짜 API를 SDK의 fetch 자리에 넣었습니다. SDK 바깥에서 흉내 내면 SDK의 응답 해석과 오류 분류를 확인할 수 없기 때문입니다.

🧩 `setup.ts`는 환경 변수에서 키, 기본 모델, 생각하는 정도(effort), 가짜 사용 여부를 읽고 SDK 클라이언트를 만듭니다. 키가 없거나 `AI_MOCK=1`이면 fetch만 `mock-anthropic.ts`로 바꿉니다. 가짜 API는 실제 API와 같은 형식으로 답해서, 가짜 fetch → SDK → `claude.ts` → 브라우저 → 컨트롤러까지 실제와 같은 경로를 지납니다. 지시문에 `[느림]`, `[한도]`, `[키]`, `[과부하]`, `[거절]`, `[잘림]`을 붙이면 각 실패 상황을 재현합니다. 모델의 지능을 흉내 내는 게 아니라, 네트워크·스트리밍·오류·검토 흐름 전체를 키 없이 검증하기 위한 모듈입니다.

### 흐름 21 — AI 결과는 제안으로만 (`ai-controller.ts`, `run.ts`)

📂 `src/lib/ai/ai-controller.ts` 37번째 줄 근처

🗣 AI 결과는 문서에 바로 쓰지 않습니다. 제안으로만 들고 있다가, 사용자가 적용을 누르면 한 번에 씁니다. 그래서 완성되지 않은 값이 다른 사람 화면에 퍼지지 않고, 실행 취소 한 번으로 되돌릴 수 있습니다.

🗣 그리고 첫 버전부터 요청할 때의 셀 값(`base`)을 기록해 두었습니다. 다음 커밋의 충돌 판단이 이 값 위에 얹혔습니다. 시트는 `SheetController`를 직접 받지 않고 `AiSheetBinding`이라는 인터페이스로만 받습니다. 그래서 `lib/ai`가 컨트롤러를 모르고, 테스트에서는 가짜로 바꿀 수 있습니다.

🧩 `AiController`가 관리하는 상태는 여섯 가지입니다. 대화 목록, 지금 생성·검토 중인 실행, 고른 모델, "원래 값 보기" 여부, 충돌 셀의 덮어쓰기 선택, 셀 잠금 여부입니다. 응답 감시도 맡습니다. 이벤트가 올 때마다 타이머를 다시 재서, 5초 동안 없으면 "응답 지연"을 표시하고 60초 동안 없으면 시간 초과로 끝냅니다. 첫 셀 제안이 오면 그 셀로 화면을 옮겨, 다른 곳을 보고 있어도 생성 과정을 볼 수 있게 합니다.

🧩 AI 요청 한 번의 상태는 `src/lib/ai/run.ts`의 `AiRun`이 표현합니다. 상태는 여덟 가지입니다. `waiting`(응답 대기), `streaming`(받는 중), `review`(검토 대기), `answered`(셀 변경 없이 답만 함), `applied`, `discarded`, `cancelled`, `error`입니다. 이벤트를 받을 때마다 `applyProgress`가 상태를 갱신하는데, 셀 제안은 네 가지를 확인합니다. 올바른 A1 주소인지, 시트 안인지, 사용자가 정한 범위 안인지, 길이가 넘지 않는지입니다. 어긋난 제안은 받지 않고 개수(`excluded`)만 셉니다. 같은 셀 제안이 다시 오면 새 것으로 바꾸고, 요청 때 값과 같은 제안은 실제 변경이 아니므로 뺍니다.

### 흐름 22 — 충돌 판단 (`coedit.ts`)

📂 `src/lib/ai/coedit.ts`, `classifyCell`

🗣 이 프로젝트에서 가장 중요하게 생각한 부분입니다. AI가 결과를 만드는 사이에 다른 사람이 같은 셀을 고칠 수 있습니다. 이때 AI가 사람의 입력을 몰래 덮어쓰면 안 됩니다.

🗣 그래서 값 세 개를 비교합니다. 요청 때 값, 현재 값, AI 제안 값입니다. (코드를 가리키며) 제안이 현재 값과 같으면 쓸 필요가 없고(`same`), 현재 값이 요청 때 값과 같으면 아무도 안 건드렸으니 적용하고(`clean`), 다르면 충돌로 보고 기본으로 건너뜁니다(`conflict`). 생성 중 수정, 검토 중 수정, 겹치는 동시 요청이라는 세 상황을 이 세 줄로 모두 처리합니다.

🗣 왜 사람의 입력을 우선했냐면, AI 결과는 다시 요청하면 또 만들 수 있지만 사람이 입력한 값은 한 번 사라지면 되살리기 어렵기 때문입니다.

🧩 충돌한 셀은 사용자가 덮어쓰기를 고를 수 있습니다. 이때 "덮어쓰기로 골랐다"만 저장하지 않고, 고를 때 본 현재 값도 함께 저장합니다. 고른 뒤에 다른 사람이 또 바꾸면 저장한 값과 현재 값이 달라지므로, 덮어쓰기 선택이 저절로 무효가 됩니다. 사용자가 덮어쓰기로 한 것은 그때 본 값이지, 그 뒤에 들어온 남의 값이 아니기 때문입니다.

🧩 이 파일에는 나머지 공동 편집 계산도 모여 있습니다. 적용·건너뛸 셀 수(`summarize`), 다른 사람에게 알릴 내 AI 작업 범위(`aiActivityOf`), 다른 사람의 AI 작업과 겹치는지(`overlappingAi`), 그중 요청을 실제로 막아야 하는 것(`blockingOverlaps`), 특정 셀에 걸친 남의 AI 작업(`aiActivitiesAt`)입니다. 모두 순수 함수라서 브라우저 없이 테스트합니다.

📂 `src/lib/ai/ai-controller.ts` 169번째 줄, `apply`

🗣 적용할 때는 먼저 제가 입력 중이던 값을 확정합니다. 그리고 화면에 보이던 판단이 아니라 현재 값으로 다시 판단하고, 판단과 쓰기를 같은 동기 코드 안에서 합니다. 그래서 그 사이에 다른 탭의 변경이 끼어들 수 없습니다.

### 🔁 흐름 따라가기 ② — AI 제안 처리 과정

🗣 AI 편집 한 번을 처음부터 끝까지 정리하면 이렇습니다.

```
 send()            제안 받는 중              검토               apply() / discard()
 ─────────▶  ───────────────────▶  ──────────────▶  ─────────────────────▶
 셀 값 찍어 둠      제안은 메모리에만         현재 값과 비교      한 트랜잭션으로 쓰기
 (base)             (문서엔 안 씀)           (same/clean/conflict) (또는 그냥 버림)
```

🗣 요청할 때는 다른 사람의 AI 작업과 겹치는지 먼저 확인하고, 비어 있지 않은 셀을 모아 보냅니다. 이 값이 요청 때 값이 됩니다. 제안은 메모리에만 있고, 화면은 문서 위에 미리보기로 겹쳐 그립니다. 다른 탭에는 제안 값이 아니라 "생성 중·검토 중, 범위, 잠금 여부"만 참여 상태로 알립니다. 검토할 때는 셀마다 세 가지로 나누고, 이 판단은 저장하지 않고 매번 현재 값과 다시 비교합니다. 그래서 바꾼 사람이 원래대로 되돌리면 충돌도 저절로 풀립니다. 적용하면 바뀔 범위로 선택을 옮긴 뒤 `ai-apply` 출처로 한 번에 씁니다. 그 뒤로는 흐름 따라가기 ①의 ④~⑤와 같은 경로로 다른 탭에 퍼집니다.

### 흐름 27 — 셀 잠금 (`locks.ts`)

📂 `src/lib/collab/locks.ts`

🗣 기본은 막지 않고 알리기만 합니다. 막으면 사람의 작업이 AI 때문에 끊기고, 확인 창을 띄우면 포커스를 빼앗아 한글 조합이 끊기기 때문입니다. 대신 "검토하는 동안은 아무도 건드리지 않았으면" 하는 경우를 위해 셀 잠금을 옵션으로 더했습니다.

🗣 이 파일의 위치를 고민했습니다. 막는 쪽은 시트 컨트롤러이고 잠그는 쪽은 AI인데, 규칙상 `collab`은 `ai`를 몰라야 합니다. 그래서 잠금을 "참여 상태를 보고 편집을 허용할지 정하는 규칙"으로 보고 여기 두었습니다.

🧩 함수는 두 개뿐입니다. `aiArea`는 범위가 null이면 시트 전체로 해석하고, `lockHolder`는 요청한 범위와 겹치는 잠금을 가진 다른 사람을 찾습니다. 예를 들어 다른 사람이 B2:D5를 잠근 상태에서 제가 C3를 편집하려 하면, `lockHolder`가 그 사람을 돌려주고 컨트롤러가 편집을 막습니다. 흐름 10의 `liveness.ts`도 Web "Lock"을 쓰지만 용도가 다릅니다. 그쪽은 탭 생존 확인이고, 이쪽은 편집 허용 판단입니다.

🗣 잠금 정보는 새 저장소를 만들지 않고, 이미 있던 AI 작업 상태에 `locked` 하나만 더했습니다. 그래서 잠근 탭이 갑자기 꺼져도, Web Locks가 그 사람의 상태를 지우면서 잠금도 함께 사라집니다. `locked`가 없는 이전 버전 탭의 상태는 잠그지 않은 것으로 봅니다.

📂 `src/lib/controller/sheet-controller.ts` 283번째 줄, `blockIfLocked`

🗣 막는 코드는 이 함수 하나입니다. 흐름 14에서 모든 명령을 컨트롤러에 모아 두었기 때문에, 입력 경로가 다섯 개여도 한 곳만 고치면 됐습니다. 잠기기 전부터 입력하던 값은 확정할 수 있게 두었습니다. 이미 입력한 글자를 버리지 않기 위해서이고, 그 셀은 흐름 22의 규칙대로 충돌로 처리됩니다.

🗣 정리하면, 이 구조를 정한 원칙은 세 가지였습니다.

🗣 첫째, 되돌리기 어려운 것부터 정했습니다. 데이터 모양, 실행 취소 기준, 탭 간 메시지 형식을 화면보다 먼저 정했고, AI가 쓸 자리도 미리 만들었습니다.

🗣 둘째, 규칙은 한 곳에만 두었습니다. 모든 입력은 컨트롤러를, 모든 쓰기는 `document.ts`를, 다른 탭에서 온 값은 `normalizePresenceState`를 지납니다. 그래서 셀 잠금처럼 나중에 생긴 규칙도 한 곳만 고치면 됐습니다.

🗣 셋째, 기준을 먼저 글로 쓰고 코드를 맞췄습니다. 지킬 수 있는 규칙은 타입과 린트로 넘겼습니다.

🗣 남은 한계도 있습니다. 탭 사이에 메시지가 오가는 아주 짧은 틈에는, 같은 셀의 동시 확정이나 잠금 전달 전의 입력을 막지 못합니다. 실제 네트워크로 넓히면 이 틈이 수백 밀리초로 늘어나기 때문에, 그때는 서버가 순서를 정하고 잠금을 관리해야 합니다. 전송 메시지 형식을 y-websocket과 맞춰 두었기 때문에, 문서를 맞추는 부분은 provider만 바꾸면 됩니다. 이상입니다.

## 부록 2: 예상 질문과 답

**Q. 왜 CRDT를 골랐나요? OT도 있지 않나요?**

OT(구글 문서 방식)는 변경 순서를 정해 주는 서버가 꼭 있어야 합니다. 이 과제는 서버 없이 탭끼리 맞춰야 했습니다. CRDT는 같은 변경을 받기만 하면 받은 순서가 달라도 같은 상태가 되므로 이 조건에 맞았습니다. 그중 Yjs를 고른 이유는 세 가지입니다. 출처별 실행 취소(UndoManager), 누가 어디를 보고 무엇을 잠갔는지 공유하는 기능(awareness), 그리고 y-websocket과 같은 메시지 형식이라 나중에 서버로 넓히기 쉽다는 점입니다.

**Q. 저장소는 왜 IndexedDB인가요?**

저장할 데이터가 Yjs의 바이너리 업데이트(Uint8Array)입니다. 브라우저 저장소 중에서 바이너리를 그대로, 비동기로, 넉넉한 용량으로 저장할 수 있는 곳은 IndexedDB뿐입니다. y-indexeddb라는 공식 연동도 있어서 직접 이을 필요가 없었습니다. 목적에 따라 나눠 썼습니다. 시트 내용은 IndexedDB, 탭별 사용자 정보는 sessionStorage, 고른 모델 같은 작은 설정은 localStorage입니다.

**Q. 같은 셀을 두 사람이 동시에 확정하면 어떻게 되나요?**

Yjs 규칙에 따라 한쪽 값만 남고, 모든 탭이 같은 결과로 맞춰집니다. 셀 값은 "100"과 "200"이 글자 단위로 섞이면 의미가 없어서 섞지 않습니다. 대신 같은 셀을 동시에 입력하면 "○○님도 이 셀을 입력 중이에요"를 띄워 서로 알아챌 수 있게 했습니다.

**Q. 제 실행 취소가 다른 사람의 입력을 지우지는 않나요?**

지우지 않습니다. 실행 취소는 이 탭에서 붙인 출처(`user-edit`, `ai-apply`)의 변경만 추적합니다. 다른 탭에서 온 변경은 출처가 provider라서 대상이 아닙니다(`undo.ts`).

**Q. AI 제안은 왜 다른 사람에게 안 보이는데, 입력 중인 글자는 보이나요?**

사람의 입력은 그 사람의 커서 테두리와 "입력 중" 이름표 안에 한 칸씩 나타나서 실제 값과 쉽게 구분됩니다. AI 제안은 범위 전체에 한꺼번에 깔려서 실제 데이터처럼 보이기 쉽습니다. 토큰이 올 때마다 모든 탭에 보내야 하는 부담도 있습니다.

**Q. 잠금을 건 탭이 갑자기 꺼지면 잠금이 남지 않나요?**

남지 않습니다. 잠금은 참여 상태에 실려 있고, 탭이 꺼지면 Web Locks가 풀리면서 다른 탭이 그 사람의 참여 상태를 바로 지웁니다. 잠금도 함께 사라집니다.

**Q. AI 결과를 적용하는 순간 다른 탭이 같은 셀을 고치면요?**

적용 코드 안에서는 판단과 쓰기를 한 번에 하므로 끼어들 수 없습니다. 다만 탭 사이를 오가는 중인 메시지까지는 막지 못합니다. 이 경우 CRDT 규칙으로 모든 탭이 둘 중 한 값으로 똑같이 맞춰집니다. 이 틈까지 없애려면 서버가 "요청 때 값이 그대로인 셀만 바꿔 달라"는 요청을 받아 확인과 쓰기를 한 번에 처리해야 합니다.

**Q. 상태 관리 라이브러리나 스프레드시트 라이브러리를 왜 안 썼나요?**

상태 관리는 읽기, 바꾸기, 알리기만 필요해서 24줄 저장소로 충분했습니다. 스프레드시트 라이브러리는 다른 사람의 커서와 AI 미리보기를 셀 위에 겹쳐 그리고, 한글 입력을 세밀하게 다루기 어려웠고 라이선스 문제도 있었습니다. 시트 크기가 100×26으로 정해져 있어서 셀을 모두 그려도 성능 문제가 없었습니다.

**Q. 테스트는 어떻게 했나요?**

로직이 모인 `lib`에 React가 없어서, 테스트 236개가 모두 Node에서 돕니다. Node에도 BroadcastChannel과 Web Locks가 있어서, 테스트 안에서 실제 세션을 여러 개 열면 탭 여러 개와 같은 경로로 동작합니다. 공동 편집과 AI가 만나는 세 상황도 세션 두 개로 재현해 검증합니다(`coedit-tabs.test.ts`). AI 전송(`AiTransport`)과 화면 조작(`SheetView`)은 바깥에서 넣을 수 있게 만들어서 가짜로 바꿔 테스트합니다.

**Q. 실제 네트워크로 넓히려면 무엇을 바꿔야 하나요?**

전송은 provider만 WebSocket으로 바꾸면 됩니다. 그 위에 서버가 맡아야 할 것이 있습니다. 원본 저장, 연결 끊김 인식(지금의 Web Locks 역할), 로그인 기반 사용자 이름, 셀 잠금, AI 적용 시 값 확인입니다. 화면에서 먼저 막는 지금 구조는 그대로 두고, 서버가 마지막으로 한 번 더 확인하는 구조가 현실적이라고 봅니다.

**Q. 구조 규칙을 왜 skill 문서로 만들었나요?**

파일을 나눌지 말지를 매번 감으로 정하면, 같은 상황에서 다른 결정이 나옵니다. 기준을 글로 남기면 사람도 AI 도구도 같은 기준으로 판단할 수 있습니다. 지킬 수 없는 예외는 이유와 함께 목록에 남겼습니다(`SheetContext.tsx`가 hook을 함께 내보내는 것).

**Q. 지금 구조에서 아쉬운 점은 무엇인가요?**

폴더를 더 나누기보다는 이름과 외부 라이브러리 경계를 다듬고 싶습니다. `collab/messages.ts`는 네트워크 메시지가 아니라 화면 문구라서 `status-messages.ts`처럼 바꾸면 덜 헷갈립니다. `locks.ts`도 Web Locks를 쓰는 `liveness.ts`와 구분되게 `ai-locks.ts`처럼 바꾸고 싶습니다. 그리고 `session.ts`와 `presence.ts`가 라이브러리 내부 값(`persistence._db`, `awareness._checkInterval`)에 기대고 있어서, 작은 어댑터로 모으면 라이브러리를 업데이트할 때 확인할 곳이 줄어듭니다.
