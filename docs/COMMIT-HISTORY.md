# 커밋으로 따라가는 구조와 설계 이유

이 문서는 저장소의 커밋을 처음부터 순서대로 따라가면서, 커밋마다 어떤 기능과 모듈이 생겼는지, 그리고 왜 그런 구조와 코드로 만들었는지를 정리합니다.

노션 문서가 "지금 각 파일이 무엇을 하는지"를 설명한다면, 이 문서는 "그 파일이 언제, 어떤 고민 끝에 그 모양이 됐는지"를 설명합니다. 커밋 diff와 그때 남긴 주석을 근거로 썼습니다.

<br>

## 0. 먼저 전체 그림부터 볼까요?

### 0.1 레이어는 한 방향으로만 흐릅니다

```
src/app          라우팅. page.tsx, AI Route Handler(route.ts)
  ↓
src/components   화면. 데이터를 읽어 그리고, 입력을 명령으로 넘김
  ↓
src/hooks        React와 lib를 잇는 구독 hook
  ↓
src/lib          React가 없는 로직
  ├─ sheet       주소·규칙·문서 읽기/쓰기·선택·이동·키 해석      (다른 lib를 모름)
  ├─ collab      세션·탭 간 전송·참여자·생존 확인·잠금·실행 취소  (ai를 모름)
  ├─ controller  SheetController: 선택·편집 상태와 시트 명령
  └─ ai          AI 요청 한 번의 생명주기, 충돌 판단
       └─ server 서버 전용: Claude 호출, 검증, 프롬프트, 가짜 API

src/resources    화면 문구·색·이름 단어 (아무것도 import하지 않음)
src/styles       디자인 토큰과 공통 클래스
```

이 모양은 처음부터 완성된 게 아닙니다. 기능을 만들면서 생긴 어긋남을 10/5와 10/8 두 번의 정리로 맞춘 결과입니다. 아래에서 그 과정을 커밋 순서대로 따라갑니다.

### `c9498cf` 프로젝트 설정과 셀 주소 모듈

**추가된 것**

- Next.js 16(App Router), TypeScript, Tailwind CSS 4, ESLint, Prettier, Vitest
- 의존성: Yjs, y-indexeddb, y-protocols, Anthropic SDK, zod
- `lib/sheet/address.ts`와 테스트

**왜 이렇게 시작했을까요?**

첫 커밋에서 이미 Yjs, y-protocols, Anthropic SDK, zod를 함께 설치했습니다. 공동 편집(CRDT), 탭 간 전송, AI 호출, 입력 검증이라는 전체 뼈대를 처음에 정하고 시작했다는 뜻입니다.

첫 코드로 `address.ts`를 고른 것도 같은 맥락입니다. 이 파일은 아무것도 import하지 않는 가장 아래 모듈이고, 모든 모듈이 셀 주소를 씁니다. 그래서 셀 주소를 두 가지 모양으로 나눠 정의했습니다.

- **A1 표기("B2", "A1:C3")**: 사람이 읽는 모양입니다. 문서의 키, AI와 주고받는 주소, 화면 표시에 씁니다.
- **좌표(`{ row, col }`)**: 계산하는 모양입니다. 선택, 이동, 위치 계산에 씁니다.

`parseA1`이 앞뒤 공백, 소문자, `$B$2` 같은 절대참조 표기까지 받아 주는 이유는, 이 함수가 사람이나 AI가 쓴 주소가 들어오는 입구이기 때문입니다.

### `be76c7f` 데이터 계층: 화면보다 먼저 만들었습니다

**추가된 모듈**

| 파일                           | 역할                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| `lib/sheet/document.ts`        | Y.Doc 읽기·쓰기. 셀을 바꾸는 코드는 모두 이 파일을 지납니다 |
| `lib/collab/broadcast-provider.ts` | BroadcastChannel로 탭끼리 문서·참여 상태를 주고받습니다 |
| `lib/collab/session.ts`        | 문서, 저장, 전송, 실행 취소를 조립하는 진입점입니다         |
| `lib/collab/undo.ts`           | 이 탭에서 한 변경만 되돌리는 UndoManager를 만듭니다         |

**왜 그리드보다 데이터 계층을 먼저 만들었을까요?**

공동 편집에서 가장 되돌리기 어려운 결정은 셀을 어떤 모양으로 저장하느냐입니다. 화면은 나중에 바꿀 수 있지만, 저장 형식을 바꾸면 이미 저장된 데이터와 다른 탭에서 돌고 있는 코드가 모두 영향을 받습니다. 그래서 이 커밋은 화면 없이, 동시 편집·늦게 합류한 탭·탭별 실행 취소·모든 탭을 닫은 뒤 복원을 테스트로 먼저 확인했습니다.

**고민 1. 셀마다 Map을 둘까요, 평평한 키로 둘까요?**

셀마다 `Y.Map`을 두는 모양이 먼저 떠오릅니다. 그런데 빈 셀 B2에 A가 값을 넣는 순간 B가 굵게를 누르면, 두 탭이 각자 B2의 Map을 새로 만들고 한쪽이 통째로 사라집니다. 그래서 최상위 Map 두 개에 평평한(flat) 키로 저장했습니다.

```
Y.Doc
├─ "values"  (Y.Map<string>)        "B2" → "100", "C3" → "합계"
└─ "formats" (Y.Map<true | string>) "B2.bold" → true, "C3.align" → "center"
```

서로 다른 키이므로 동시에 바뀌어도 두 변경이 모두 남습니다. 값과 서식을 다른 Map에 둔 덕분에, Delete로 값만 지우거나 AI에 보낼 셀 목록을 만들 때 서식을 걸러낼 필요가 없습니다.

**고민 2. 실행 취소는 무엇을 기준으로 나눌까요?**

`document.ts`의 모든 쓰기 함수는 `origin`을 인자로 받고, 트랜잭션에 출처를 붙입니다.

```ts
export const EditOrigin = {
  User: "user-edit",
  Ai: "ai-apply",
} as const;
```

눈여겨볼 점은 `EditOrigin.Ai`가 AI 기능을 만들기 하루 전, 이 첫 데이터 계층 커밋에 이미 있었다는 것입니다. `undo.ts`의 UndoManager는 이 두 출처만 추적합니다. 다른 탭에서 온 변경은 출처가 provider라서 추적하지 않으므로, 내 실행 취소가 다른 사람의 입력을 지우지 않습니다. AI 결과는 한 트랜잭션으로 쓰기만 하면 실행 취소 한 번으로 모두 되돌아갑니다. 실행 취소 구조는 나중에 바꾸기 어렵기 때문에, AI가 들어올 자리를 처음부터 만들어 둔 것입니다.

`captureTimeout: 0`도 이때 정했습니다. Yjs 기본값(500ms)이면 빠르게 이어진 편집이 한 단계로 합쳐집니다. 스프레드시트에서는 "동작 하나 = 트랜잭션 하나 = 실행 취소 한 단계"가 자연스럽다고 판단했습니다.

**고민 3. 탭 간 전송은 왜 직접 만들었을까요?**

조건이 "서버 없이, 브라우저 API만"이었습니다. 그래서 BroadcastChannel 위에서 동작하는 provider를 직접 만들었습니다. 다만 메시지 형식은 y-websocket과 같은 y-protocols 인코딩(메시지 번호 0: 문서 동기화, 1: 참여 상태, 3: 참여 상태 요청)을 그대로 썼습니다. 네트워크 동기화로 넓힐 때 이 클래스만 `WebsocketProvider`로 바꾸면 되게 하기 위해서입니다.

WebSocket은 서버와 1:1이지만 BroadcastChannel은 1:N 방송입니다. 이 차이 때문에 세 가지를 코드로 정했습니다.

- 합류할 때 SyncStep1(내가 가진 변경 목록)과 SyncStep2(내 전체 상태)를 방송합니다. 답장이 모든 탭에 가도 Yjs 업데이트는 멱등이라 안전합니다.
- `handleDocUpdate`는 `origin === this`면 방송하지 않습니다. 받은 변경을 다시 보내면 탭끼리 같은 변경을 끝없이 주고받습니다.
- 참여 상태는 자기 것만 보냅니다. 다른 탭의 상태를 중계하면, 타임아웃으로 지운 상태가 다시 퍼지면서 살아 있는 사용자가 목록에서 깜빡입니다.

**고민 4. 부품은 어디서 조립할까요?**

`session.ts`의 `createSheetSession`이 문서 하나에 저장 부품(IndexedDB)과 전송 부품(BroadcastChannel)을 각각 붙입니다. 문서와 화면은 저장·전송 방식을 모르므로, 어느 쪽을 바꿔도 이 파일만 고치면 됩니다.

### `189d4b4` 그리드와 셀 선택·키보드 이동·편집

**추가된 모듈**

- 화면: `SheetApp`, `Grid`(한 파일 576줄), `GridCells`, `GridHeaders`, `FormulaBar`, `useSheetSession`
- 로직: `keymap.ts`(키 → 동작), `selection.ts`(선택 연산), `geometry.ts`(좌표 → 픽셀), `store.ts`, `platform.ts`

**이 시점의 구조**

이 커밋의 `Grid.tsx`는 편집 상태(`editStore`)와 명령(`startEdit`, `commitEdit`, `runAction`), 마우스 처리, 스크롤까지 모두 들고 있었습니다. 동작을 먼저 맞추는 단계였기 때문입니다. 다만 키 해석(`keymap.ts`)과 선택 연산(`selection.ts`)은 처음부터 순수 함수로 빼고 테스트를 붙였습니다. 엑셀 규칙은 경우의 수가 많아서, 화면에서 손으로 확인하기보다 테스트로 고정하는 편이 안전했습니다.

**가장 오래 고민한 곳: 한글 입력**

스프레드시트는 "셀을 고르고 바로 타이핑"이 기본입니다. 그런데 타이핑을 시작하는 순간 포커스를 편집칸으로 옮기면, 한글 조합이 끊기고 첫 자모가 사라집니다. 커밋에 남은 주석을 보면 이렇게 풀었습니다.

- 셀 편집기는 항상 DOM에 남아 포커스를 유지하고, 편집 중이 아닐 때는 투명하게 active 셀 위에 있습니다. 첫 글자부터 같은 칸에서 조합됩니다.
- 값은 비제어(uncontrolled)로 다룹니다. React가 조합 중인 값을 덮어쓰면 한글 입력이 깨지기 때문입니다.
- IME 조합 중인 키는 입력기에 맡깁니다. 여기서 Enter를 처리하면 마지막 글자가 사라지거나 두 번 들어갑니다.
- 다른 창·탭으로 전환해서 포커스를 잃으면 편집을 유지합니다. 돌아오면 이어서 입력할 수 있게 하기 위해서입니다.

**`store.ts`를 직접 만든 이유**

키를 누르는 순간에는 다음 화면이 그려지기를 기다리지 않고 최신 선택 위치를 바로 읽어야 합니다. React state만 쓰면 이벤트 핸들러가 이전 값을 읽을 수 있어서 state와 ref를 같이 맞춰야 하고, 그 사이에 값이 어긋날 틈이 생깁니다. 필요한 기능은 읽기, 바꾸기, 알리기 세 가지뿐이라 24줄짜리 저장소를 만들었습니다.

이때는 `store.ts` 안에 React를 쓰는 `useStore`가 같이 있었습니다. 나중에 "lib에는 React가 없다"는 규칙을 세우면서 `hooks/useStore.ts`로 옮깁니다(`42d8ef5`).

**셀 값은 화면에 복사하지 않습니다**

`useDocVersion`은 문서가 바뀔 때마다 숫자 하나만 올립니다. 화면은 이 숫자가 바뀌면 다시 그리고, 그릴 때마다 Y.Doc에서 직접 값을 읽습니다. 원본이 하나뿐이라 원본과 복사본이 어긋날 일이 없습니다. `useSheetSession`은 저장된 내용을 다 불러온 뒤에 세션을 돌려줍니다. 빈 시트가 잠깐 보였다가 채워지는 깜빡임을 막기 위해서입니다.

### `90c202e` 서식 툴바

**추가된 것**: `Toolbar.tsx`, `useUndoState.ts`, `document.ts`의 값 서식

**왜 서식을 두 종류로 나눴을까요?**

굵게·기울임처럼 켜고 끄는 서식(`FORMAT_KEYS`, 값은 `true`)과, 글자색·채우기·정렬처럼 값을 갖는 서식(`STYLE_KEYS`, 값은 문자열)은 다루는 방법이 다릅니다. 켜고 끄는 서식은 "범위 전체에 켜져 있으면 끄고, 하나라도 꺼져 있으면 모두 켠다"(구글 시트와 같음)이고, 값 서식은 "같은 값이면 그 값, 섞여 있으면 null"(`commonStyle`, 툴바 표시용)입니다.

값 서식은 `isValidStyle`로 형식을 검증합니다. 주석에 따르면 "다른 탭·AI에서 온 값도 같은 함수를 거친다"는 것이 이유입니다. 문서에 잘못된 값이 들어와도 `getFormat`이 읽을 때 걸러냅니다.

### `f63fb07` 참여자 표시

**추가된 모듈**: `lib/collab/presence.ts`, `identity.ts`, `ParticipantList`, `RemoteCursors`, `useDismiss`

**고민 1. 탭이 닫힌 것은 어떻게 알까요?**

y-protocols의 기본 방식은 각 탭이 15초마다 자기 상태를 갱신하고, 30초 동안 소식이 없는 탭을 지우는 것입니다. 그런데 커밋의 주석에 적었듯이, 크롬은 5분 넘게 가려진 탭의 타이머를 1분에 한 번으로 늦춥니다. 그래서 열려 있는 탭이 목록에서 사라졌다 나타났습니다.

그래서 Web Locks로 바꿨습니다.

1. 각 탭은 자기 번호(clientID) 이름의 잠금을 쥔 다음에 참여 상태를 공개합니다.
2. 다른 탭은 그 잠금을 요청해 두고 기다립니다.
3. 탭이 닫히거나 죽으면 브라우저가 잠금을 풀고, 기다리던 탭에 잠금이 넘어오는 순간 그 사용자를 지웁니다.

순서가 중요합니다. 잠금을 쥐기 전에 상태를 공개하면, 다른 탭이 비어 있는 잠금을 보고 나를 이미 떠난 사용자로 볼 수 있습니다. Web Locks가 없는 환경에서는 기본 방식을 그대로 씁니다.

**고민 2. 이름이나 색이 겹치면 누가 바꿀까요?**

번호(clientID)가 큰 쪽이 양보합니다. 서로 묻지 않아도 양쪽이 같은 규칙을 따르므로, 정확히 한쪽만 바뀝니다. 탭을 복제해서 sessionStorage가 그대로 복사된 경우도 이 규칙으로 풀립니다.

**고민 3. 사용자 정보는 어디에 저장할까요?**

sessionStorage에 저장했습니다. 탭마다 따로 있어서 새 탭은 새 사용자가 되고, 같은 탭을 새로고침하면 같은 이름으로 돌아옵니다. 읽고 쓰는 일은 `identity.ts`의 `loadTabUser`·`saveTabUser`가 맡고, 세션과 `Presence`는 처음 이름(`user`)과 바뀌었을 때 부를 콜백(`onUserChange`)만 받습니다. 둘을 잇는 것은 `useSheetSession`입니다. 그래서 `Presence`는 저장 방식과 상관없이 테스트할 수 있습니다.

이 커밋에서 provider에 `resync()`, 세션에 `leave()`·`rejoin()`도 생겼습니다. 탭을 닫으면(`pagehide`) 바로 목록에서 빠지고, 뒤로/앞으로 가기 캐시(bfcache)에서 복원되면 멈춰 있던 동안 놓친 변경을 합류 절차로 다시 받습니다.

이때의 `presence.ts`는 상태 타입, 색 목록, 이름 단어, Web Locks 로직을 한 파일에 모두 담고 있었습니다. 10/5에 책임별로 나뉩니다(`516d2e6`, `734a13d`).

파일 하나가 경계 하나를 맡도록 나눴습니다. 신뢰할 수 없는 데이터가 들어오는 곳(브라우저 입력, 모델 출력, 환경 변수)마다 검사하는 파일이 따로 있어서, 어디서 무엇을 검사하는지 찾기 쉽습니다.

**고민 1. 결과를 어떻게 받을까요?**

AI가 쓴 글에서 셀 값을 찾아내는 대신, `propose_edits` 도구 호출로 `{ cell, value }` 목록을 받았습니다. 형식이 확실하고, AI의 설명과 실제 편집이 나뉩니다. 도구 입력을 스트리밍으로 받으면 셀 제안을 하나씩 미리보기에 보여 줄 수 있습니다.

그런데 SDK의 부분 JSON 해석은 잘린 문자열도 받아들일 수 있습니다. 그러면 `"1250"`이 아니라 `"12"` 같은 덜 만들어진 값이 제안으로 보입니다. 그래서 `edit-stream-parser.ts`를 직접 만들었습니다. 문자열 안인지, 이스케이프 중인지, 어떤 괄호가 열려 있는지를 추적하다가 `edits` 배열 안의 객체가 완전히 닫혔을 때만 `JSON.parse`를 실행합니다.

**고민 2. 브라우저와는 어떻게 주고받을까요?**

요청에 시트 내용을 실어야 해서 POST가 필요했습니다. 브라우저 기본 스트리밍(EventSource)은 GET만 지원해서, fetch 응답을 한 줄씩 읽는 NDJSON을 택했습니다. 줄을 나눠 `JSON.parse`하면 되고, `AbortController`로 끊을 수도 있습니다.

응답을 보내기 시작하면 HTTP 상태 코드를 바꿀 수 없습니다. 그래서 `route.ts`는 첫 이벤트를 받은 뒤에 스트림을 엽니다. 키 오류나 요청 한도처럼 시작 전에 실패하면 HTTP 상태로, 시작한 뒤에 실패하면 스트림 안의 `error` 이벤트로 알립니다.

**고민 3. 키 없이 어떻게 테스트할까요?**

`setup.ts`는 키가 없거나 `AI_MOCK=1`이면 SDK의 `fetch` 자리에만 가짜 구현을 넣습니다. 서버 함수 바깥에서 응답을 흉내 내면, SDK가 응답을 해석하고 오류를 분류하는 부분은 확인할 수 없기 때문입니다. 가짜 API는 실제 API와 같은 SSE 형식으로 답하고, 지시문의 `[느림]`, `[한도]`, `[거절]` 같은 표시로 실패 상황도 재현합니다.

이 커밋의 `protocol.ts`에는 오류 문구(한국어)가 들어 있어서 서버와 브라우저가 같은 문구를 보냈습니다. 이 결정은 다음 날 바뀝니다(`345425f`).


주석에 남긴 이유는 "AI 결과는 다시 만들기 쉽지만 사람의 입력은 그렇지 않다"입니다. 그래서 사람이 바꾼 셀을 AI가 몰래 덮어쓰지 않게 했습니다.

**판단 결과는 저장하지 않습니다**

`states()`는 부를 때마다 현재 값과 다시 비교합니다. 다른 사용자가 값을 원래대로 되돌리면 충돌도 저절로 풀립니다. 덮어쓰기를 골라도 "고를 때 본 값"에 묶입니다(`overwrites`: 셀 → 고를 때 본 값). 그 뒤에 값이 또 바뀌었다면 내가 보지 못한 다른 사람의 새 값이므로, 다시 고를 때까지 건너뜁니다.

**다른 사람에게는 범위와 상태만 알립니다**

`AiActivity`(생성 중/검토 중, 범위)를 참여 상태에 싣고, 제안 값은 싣지 않습니다. 확정되지 않은 값이 실제 데이터처럼 보이면 혼란스럽고, 토큰마다 모든 탭에 방송해야 하기 때문입니다. `publishActivity`는 상태나 범위가 바뀔 때만 알립니다.

**막지 않고 알립니다**

다른 사용자의 AI 편집 범위에서 입력하거나 겹쳐 요청해도 막지 않고 안내만 띄웁니다. 막으면 사람의 작업 흐름이 끊기고, 확인 창으로 물으면 편집칸의 포커스를 빼앗아 한글 조합이 끊깁니다. 막지 않아도 위의 충돌 규칙이 사람의 입력을 지켜 줍니다.

**이 시점에 남은 문제**

`coedit.ts`가 `ai-controller.ts`에서 `AiProposal` 타입을 가져오고, `ai-controller.ts`는 `coedit.ts`를 import하는 순환이 생겼습니다. 다음 날 구조 규칙의 첫 예외 목록에 올라갑니다.

## 4단계 (10/6~10/7): 공동 편집과 AI가 만나는 지점을 보강했습니다

### `d38b4a2` AI 편집 시 셀 잠금

**왜 옵션으로 더했을까요?**

기본(막지 않고 알리기)은 그대로 두었습니다. 다만 "검토하는 동안만큼은 아무도 건드리지 않았으면 좋겠다"는 경우를 위해, 툴바의 **AI 편집 시 셀 잠금**을 켜면 막는(hard lock) 옵션을 더했습니다.

**잠금은 어디에 둘까요? → `lib/collab/locks.ts`**

잠금을 막는 쪽은 `SheetController`(`lib/controller`)이고, 잠금 정보를 만드는 쪽은 AI 실행입니다. 그런데 규칙상 `lib/collab`은 `lib/ai`를 몰라야 합니다. 그래서 잠금을 "참여 상태를 보고 편집을 허용할지 정하는 참여자 사이의 규칙"으로 보고 `lib/collab/locks.ts`에 두었습니다. `aiArea`(null이면 시트 전체)와 `lockHolder`(겹치는 잠금을 가진 다른 사용자 찾기)만 있는 작은 파일입니다. 컨트롤러와 `coedit.ts`가 모두 이 파일을 봅니다.

**잠금 정보는 새로 만들지 않고 참여 상태에 얹었습니다**

`AiActivity`에 `locked` 하나를 더했습니다. 따로 저장소를 만들지 않았기 때문에 얻은 것이 두 가지입니다.

- 잠근 탭이 비정상적으로 종료되면, Web Locks가 그 사용자의 참여 상태를 지우면서 잠금도 함께 사라집니다. 잠금이 남는 일이 없습니다.
- `locked`가 없는 상태(이전 버전 탭)는 잠그지 않은 것으로 봅니다. 배포 중에 버전이 섞여도 깨지지 않습니다.

**정한 규칙들**

- 잠근 실행은 요청한 범위를 그대로 알립니다. 제안이 오면서 범위가 바뀌면 어느 셀이 잠겼는지 예측할 수 없기 때문입니다.
- `blockingOverlaps`: 남이 잠근 범위에는 요청할 수 없고, 내가 잠그려면 겹치는 AI 편집이 없어야 합니다. 그래서 잠긴 범위에는 AI 실행이 하나뿐입니다.
- 입력 시작, 지우기, 서식 변경이 모두 `refuseLocked`(나중에 `blockIfLocked`)를 지납니다. 명령을 컨트롤러 한 곳에 모아 두었기 때문에, 막는 코드도 하나면 됐습니다.
- 바로 타이핑해서 시작하려다 막히면, 편집칸에 이미 들어간 글자를 지웁니다. 한글 조합 중이었다면 `useCellEditor`가 조합한 글자도 지웁니다.
- 잠기기 전부터 입력하던 값은 확정할 수 있습니다. 이미 입력한 글자를 버리지 않기 위해서이고, 그 셀은 충돌 규칙으로 처리됩니다.

이 커밋에서 `Toolbar.tsx`를 `toolbar/` 폴더(`index.tsx`, `ColorMenu.tsx`)로 나누면서, SKILL.md의 예외 목록이 처음으로 "없음"이 됐습니다.

<br>

### `2c03693` 입력 중인 값을 확정 전에도 보여 줍니다

**왜 문서가 아니라 참여 상태에 실었을까요?**

입력 중인 값을 문서에 쓰면 저장되고, 실행 취소 기록에도 남습니다. 그래서 커서와 같은 경로(awareness)에 `draft` 필드를 더했습니다. 확정하기 전까지는 저장되지 않고, Esc로 취소하면 다른 화면에서도 원래 값으로 돌아갑니다. 0.2의 원칙("확정되지 않은 것은 문서에 넣지 않는다")을 그대로 적용한 것입니다.

**코드에서 정한 것**

- `DRAFT_MAX_LENGTH = 1000`: 한 글자마다 모든 탭에 보내므로 크기를 제한하고, 값이 바뀌었을 때만 보냅니다.
- `setEditing`은 편집을 끝내면 `draft`도 함께 지웁니다. 확정 후에 이전 글자가 남아 보이지 않게 하기 위해서입니다.
- `draftChanged`는 한글 조합 중인 글자도 알립니다. 입력하는 모습이 그대로 보이게 하기 위해서입니다.
- `RemoteDrafts`는 셀 서식을 따르고 셀 너비에서 자릅니다. 넘치게 그리면 같은 셀을 입력 중인 내 편집칸 옆으로 삐져나오기 때문입니다.

AI 제안은 숨기면서 사람의 입력은 보여 주는 이유는 이렇게 구분했습니다. 사람의 입력은 그 사람의 커서 테두리와 "입력 중" 이름표 안에 한 칸씩 나타나서 실제 값과 쉽게 구분되지만, AI 제안은 범위 전체에 한꺼번에 깔려서 실제 데이터처럼 보이기 쉽습니다.

<br>

### `53b0784` 수식 입력줄에서도 셀 값을 고칩니다

**왜 별도의 편집 경로를 만들지 않았을까요?**

수식 입력줄에 따로 편집 상태를 두면, 확정·이동·실행 취소·잠금·다른 사용자 알림을 모두 다시 만들어야 합니다. 그래서 `replaceDraft(text)`가 수식 입력줄의 글자를 셀 편집칸에도 똑같이 써 넣게 했습니다. 셀 편집칸이 여전히 원본이므로, 나머지 규칙은 셀에서 입력할 때와 같습니다. 두 칸이 같은 글자를 보여 주도록 컨트롤러에 `draft` 저장소도 더했습니다.

**두 칸 사이로 포커스를 옮길 때는 확정하지 않습니다**

`lib/sheet/draft-input.ts`가 두 칸에 같은 표시(`data-draft-input`)를 붙이고, `isDraftInput`으로 확인합니다. 포커스가 표시가 붙은 칸 사이에서 옮겨 갈 때는 같은 편집 작업으로 보고 확정하지 않습니다.

`useFormulaInput`도 셀 편집칸처럼 비제어 input입니다. 잠긴 셀이라 편집을 시작하지 못하면, 입력한 글자를 지우고 셀 값으로 되돌립니다.

## 마치며: 구조를 관통하는 결정

커밋을 따라가 보면, 구조를 정한 결정은 결국 세 가지로 모입니다.

**1. 되돌리기 어려운 것부터 정했습니다**

데이터 모양(평평한 키), 실행 취소 기준(출처), 탭 간 메시지 형식(y-protocols)을 화면보다 먼저 정했습니다. AI 적용 출처(`EditOrigin.Ai`)와 요청 때 값(`base`)처럼, 나중에 올 기능이 쓸 자리도 미리 만들어 두었습니다.

**2. 규칙은 한 곳에만 둡니다**

모든 입력 경로가 `SheetController`의 같은 명령을 지나고, 셀을 바꾸는 코드는 모두 `document.ts`를 지나고, 다른 탭에서 온 값은 `normalizePresenceState`에서 한 번만 맞춥니다. 그래서 셀 잠금처럼 나중에 생긴 규칙도 한 곳만 고치면 됐습니다.

**3. 기준을 먼저 쓰고, 어긋난 곳을 목록으로 지웠습니다**

SKILL.md에 기준과 예외 목록을 함께 적고, 커밋마다 목록을 지웠습니다. 지킬 수 없는 예외는 이유와 함께 남겼고, 지킬 수 있는 규칙은 타입(`AiModelId`)과 린트(`import/order`)로 넘겼습니다.
