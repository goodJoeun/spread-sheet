## 1. 무엇부터 만들었을까요?

### 1.1 화면보다 데이터 모양을 먼저 정했습니다

첫 기능 커밋(`be76c7f`)은 그리드가 아니라 데이터 계층입니다. 공동 편집에서 가장 되돌리기 어려운 결정은 "셀을 어떤 모양으로 저장하느냐"이기 때문입니다. 화면은 나중에 얼마든지 바꿀 수 있지만, 저장 형식을 바꾸면 이미 저장된 데이터와 다른 탭에서 돌고 있는 코드가 모두 영향을 받습니다.

그래서 화면을 그리기 전에 아래 네 가지를 먼저 정하고, 테스트로 확인했습니다.

- 같은 셀을 동시에 바꾸면 모든 탭이 같은 값으로 맞춰지는가
- 늦게 연 탭도 앞선 내용을 따라잡는가
- 실행 취소가 내 변경만 되돌리는가
- 모든 탭을 닫았다 다시 열어도 내용이 남는가

<br>

### 1.2 왜 CRDT(Yjs)였을까요?

조건은 "서버 없이, 같은 브라우저의 탭끼리" 동기화하는 것이었습니다. 순서를 정해 줄 서버가 없으니, 변경을 받은 순서가 탭마다 달라도 결과가 같아야 했습니다. CRDT는 바로 이 성질을 가진 자료구조입니다.

직접 만드는 방법도 생각할 수 있었습니다. 하지만 그러면 수렴, 늦게 합류한 탭의 따라잡기, "내 변경만 실행 취소"를 모두 손으로 풀어야 합니다. Yjs에는 사용자 정보를 주고받는 기능(awareness)과 출처별 실행 취소(UndoManager)가 함께 있어서, 이 프로젝트에 필요한 부품이 거의 다 있었습니다.

<br>

### 1.3 셀마다 객체를 두지 않고 평평한 키로 저장했습니다

처음에 자연스러워 보이는 모양은 "셀마다 `Y.Map` 하나"입니다. 그런데 빈 셀 B2에 A가 값을 넣는 순간 B가 굵게를 누르면, 두 탭이 각자 B2의 Map을 새로 만듭니다. 그러면 한쪽 Map이 이기고, 다른 쪽 변경은 통째로 사라집니다.

그래서 값은 `"B2" → "100"`, 서식은 `"B2.bold" → true`처럼 평평한(flat) 키로 저장했습니다. 서로 다른 키이므로 두 변경이 모두 남습니다.

- 코드: [document.ts](../src/lib/sheet/document.ts) 맨 위 주석
- 확인: [document.test.ts](../tests/unit/sheet/document.test.ts)의 `concurrent edits`

값과 서식을 다른 Map에 둔 것도 같은 결정의 일부입니다. AI에 보낼 셀 목록을 만들거나 Delete로 값만 지울 때, 서식을 걸러낼 필요가 없습니다.

<br>

### 1.4 모든 변경에 출처를 붙였습니다

셀을 바꾸는 코드는 모두 [document.ts](../src/lib/sheet/document.ts)를 지나고, 변경마다 출처(origin)를 붙입니다. 사람이 고쳤으면 `"user-edit"`, AI 결과를 적용했으면 `"ai-apply"`입니다.

왜 이렇게 했을까요? 실행 취소가 "이 탭에서 한 변경"만 되돌려야 하기 때문입니다. [undo.ts](../src/lib/collab/undo.ts)의 UndoManager는 이 두 출처만 추적합니다. 다른 탭에서 온 변경은 출처가 provider라서 추적 대상이 아닙니다. 그래서 내 Ctrl+Z가 다른 사람의 입력을 지우지 않습니다.

처음 계획에서는 AI 결과를 적용하기 전후로 `stopCapturing()`을 불러 실행 취소 단계를 끊으려고 했습니다. 구현하면서 `captureTimeout: 0`으로 바꿨습니다. 그러면 모든 동작이 원래 한 단계가 되어 따로 끊을 필요가 없습니다. 함께 [writeValues](../src/lib/sheet/document.ts#L71)는 값이 그대로인 셀은 쓰지 않게 해서, 아무것도 바뀌지 않은 실행 취소 단계가 생기지 않게 했습니다.

<br>

### 1.5 탭 간 전송은 나중에 바꿀 것을 생각하고 만들었습니다

[broadcast-provider.ts](../src/lib/collab/broadcast-provider.ts)는 BroadcastChannel 위에서 y-websocket과 같은 메시지 형식(y-protocols)을 씁니다. 그래서 네트워크 동기화로 넓힐 때 이 부품만 `WebsocketProvider`로 바꾸면 됩니다.

다만 WebSocket은 서버와 1:1로 연결되고, BroadcastChannel은 모든 탭에 한꺼번에 방송합니다. 이 차이 때문에 두 가지를 정했습니다.

- 다른 탭에서 받은 변경은 다시 보내지 않습니다. 다시 보내면 탭끼리 같은 변경을 끝없이 주고받습니다.
- 사용자 정보는 자기 것만 보냅니다. 다른 탭의 정보를 대신 보내면, 이미 떠난 사용자가 되살아나 목록이 깜빡입니다.

조립은 [session.ts](../src/lib/collab/session.ts) 한 곳에서 합니다. 문서 하나에 저장 부품(IndexedDB)과 전송 부품(BroadcastChannel)을 각각 붙이므로, 어느 쪽을 바꿔도 문서와 화면은 그대로입니다.

<br>

## 2. 시트 기본기는 어떻게 만들었을까요?

### 2.1 그리드를 직접 만들었습니다

다른 사용자의 커서와 AI 미리보기를 셀 위에 겹쳐 그려야 했고, 한글 입력을 세밀하게 다뤄야 했습니다. 기존 스프레드시트 라이브러리로는 이 부분을 바꾸기 어렵고, 라이선스 문제도 있었습니다.

대신 범위를 좁혔습니다. 시트 크기를 100×26으로 정해 두었기 때문에, 보이는 셀만 그리는 기법(가상 스크롤) 없이 2,600개를 그대로 그려도 충분했습니다. 겹쳐 그리는 순서(내 선택, 다른 사용자 커서, 이름표)는 흩어져 있던 z-index를 [layers.ts](../src/components/sheet/grid/layers.ts) 한 곳으로 모았습니다(`2e70de6`).

<br>

### 2.2 한글 입력에서 가장 많이 고민했습니다

스프레드시트는 "셀을 고르고 바로 타이핑"하는 흐름이 기본입니다. 그런데 타이핑을 시작하는 순간 포커스를 편집칸으로 옮기면, 한글 조합이 끊기고 첫 자모가 사라집니다.

그래서 이렇게 풀었습니다.

- **보이지 않는 편집칸이 늘 선택한 셀 위에서 포커스를 갖고 있습니다.** 첫 글자부터 같은 칸에서 조합되고, 입력기 후보창도 셀 위치에 뜹니다.
- **편집칸의 값은 React가 관리하지 않습니다(비제어 input).** React가 다시 그릴 때마다 값을 덮어쓰면 조합 중인 글자가 깨지기 때문입니다. 컨트롤러는 필요할 때만 `SheetView.readDraft()`·`writeDraft()`로 읽고 씁니다.
- **조합 중에 누른 키는 시트가 처리하지 않습니다.** 글자를 확정하려고 누른 Enter를 셀 이동으로 처리하면, 마지막 글자가 사라지거나 두 번 들어갑니다. 이 판정(`keyCode 229`)은 처음에 세 곳에 따로 있었는데, 나중에 `isImeComposing` 하나로 모았습니다(`d110181`).

같은 이유로 "확인 창"은 쓰지 않았습니다. 확인 창이 포커스를 빼앗으면 조합이 중간에 끊깁니다. 이 제약은 뒤에서 AI 편집 범위를 알리는 방식을 정할 때도 영향을 줬습니다(4.4).

<br>

### 2.3 576줄짜리 그리드를 나누면서 컨트롤러가 생겼습니다

처음 구현한 `Grid`는 키보드, 마우스, 편집, 스크롤을 모두 들고 있는 576줄짜리 컴포넌트였습니다. 툴바와 참여자 목록이 붙자 문제가 드러났습니다. 셀을 바꾸는 입력 경로가 여러 개가 되면서, "편집 중이면 먼저 확정한다" 같은 규칙을 경로마다 따로 지켜야 했습니다.

그래서 세 단계로 나눴습니다.

1. **이동 규칙을 순수 함수로 뺐습니다**(`a525359`). Tab 다음 Enter는 시작 열로 돌아가기, Ctrl+방향키는 데이터 끝으로 같은 엑셀 규칙을 선택 상태만으로 계산합니다. 지금 이름은 [applyNavigation](../src/lib/sheet/navigation.ts#L48)입니다.
2. **명령을 [SheetController](../src/lib/controller/sheet-controller.ts) 한 곳에 모았습니다**(`5603cf4`). 키보드, 마우스, 툴바, 참여자 목록, AI 패널이 모두 같은 명령을 부릅니다. 스크롤·포커스처럼 DOM이 필요한 일은 `SheetView` 인터페이스로 그리드에 맡겨서, 컨트롤러는 화면 없이 테스트할 수 있습니다.
3. **그리드를 역할별로 나눴습니다**(`4b195c4`). 키보드·한글 입력은 `useCellEditor`, 마우스는 `useGridPointer`, 겹쳐 그리는 것은 각자의 컴포넌트로 갔습니다. 세션과 컨트롤러는 Context로 내려 주어 props 전달을 없앴습니다.

키 처리도 "어떤 키인지 → 어떤 동작인지 → 어떤 명령을 실행할지"로 나눴습니다. 앞의 두 단계([resolveGridKey](../src/lib/sheet/keymap.ts#L93), `applyNavigation`)는 입력만 있으면 결과가 정해지는 함수라, 엑셀 규칙을 브라우저 없이 테스트할 수 있습니다.

<br>

### 2.4 상태 관리 라이브러리 대신 24줄짜리 저장소를 만들었습니다

키를 누르는 순간에는 다음 화면이 그려지기를 기다리지 않고 최신 선택 위치를 바로 읽어야 합니다. React state만 쓰면 이벤트 핸들러가 이전 값을 읽을 수 있어서, state와 ref를 같이 맞춰야 합니다. 그 사이에 값이 어긋날 틈이 생깁니다.

필요한 기능은 값 읽기, 값 바꾸기, 바뀌면 알리기 세 가지뿐이었습니다. 그래서 [store.ts](../src/lib/store.ts)를 직접 만들고, 화면은 React 표준 방식인 `useSyncExternalStore`로 구독만 하게 했습니다. 셀 값은 이 저장소에도 복사하지 않습니다. 화면은 "문서가 바뀌었다"는 신호만 받고, 그릴 때마다 Y.Doc에서 직접 읽습니다. 원본이 하나뿐이라 어긋날 일이 없습니다.

<br>

### 2.5 실제로 멈춰 보고 고친 것: 저장소를 열 수 없을 때

빈 시트가 잠깐 보였다가 내용이 채워지는 게 어색해서, 저장된 내용을 다 불러온 뒤에 시트를 보여 주게 했습니다. 그런데 y-indexeddb는 불러오기 성공만 알려 주고 실패는 알려 주지 않습니다. 저장소가 막힌 브라우저에서는 로딩 화면이 끝나지 않았습니다.

그래서 [session.ts](../src/lib/collab/session.ts#L59)에서 "불러오기 성공, 저장소 열기 실패, 5초 경과" 중 먼저 오는 것으로 정하게 고쳤습니다(`17df456`). 저장소를 못 열어도 탭 간 동기화는 그대로 되고, 경고 띠만 보여 줍니다.

<br>

## 3. 다른 사용자는 어떻게 보이게 했을까요?

### 3.1 탭이 닫힌 것은 타이머가 아니라 Web Locks로 알아챕니다

처음 계획은 y-protocols의 기본 방식이었습니다. 각 탭이 15초마다 자기 상태를 갱신하고, 30초 동안 소식이 없는 탭을 지우는 방식입니다. 그런데 크롬은 가려진 탭의 타이머를 늦춥니다. 그래서 열려 있는 탭이 목록에서 사라졌다가 다시 나타났습니다.

그래서 [liveness.ts](../src/lib/collab/liveness.ts)에서 방식을 바꿨습니다. 각 탭은 자기 번호(clientID) 이름의 잠금을 쥐고 있고, 다른 탭은 그 잠금을 기다립니다. 탭이 닫히면 브라우저가 잠금을 풀어 주므로, 기다리던 탭이 즉시 알아챕니다. Web Locks가 없는 환경에서는 기본 방식으로 돌아갑니다.

이 결정은 뒤에서 셀 잠금을 만들 때 도움이 됐습니다. 잠금 정보를 사용자 정보에 실어 두었기 때문에, 잠근 탭이 비정상적으로 종료되어도 잠금이 남지 않습니다.

[join](../src/lib/collab/presence.ts#L57)은 잠금을 쥔 다음에 내 상태를 공개합니다. 순서가 반대면, 다른 탭이 잠금이 비어 있는 것을 보고 나를 이미 떠난 사용자로 볼 수 있기 때문입니다.

<br>

### 3.2 이름이나 색이 겹치면 번호가 큰 쪽이 양보합니다

처음에는 탭을 복제했을 때 sessionStorage가 복사되는 경우만 따로 감지하려고 했습니다. 그러다 우연히 겹친 경우까지 하나의 규칙으로 풀기로 했습니다.

[resolveConflicts](../src/lib/collab/presence.ts#L150)는 나보다 번호가 작은 탭과 겹칠 때만 내 이름·색을 바꿉니다. 서로 묻지 않아도 양쪽이 같은 규칙을 따르므로, 정확히 한쪽만 바뀝니다.

<br>

### 3.3 다른 탭에서 온 값은 들어오는 곳에서 한 번만 맞춥니다

다른 탭은 이전 버전의 코드로 돌고 있을 수도 있습니다. 처음에는 커서, 참여자 목록, AI 범위 표시, 충돌 판단 등 다섯 곳이 각자 좌표를 시트 안으로 맞추고 있었습니다.

이걸 [normalizePresenceState](../src/lib/collab/presence-state.ts#L92) 한 곳으로 모았습니다(`456f88e`). 참여자 목록을 만들 때 형식을 확인하고 좌표를 맞추면, 목록을 쓰는 쪽은 그대로 믿고 씁니다. 이렇게 모으는 과정에서, 참여자 목록이 시트 밖 AI 범위를 그대로 그리다 음수 열에서 예외가 나던 문제도 함께 막혔습니다.

<br>

## 4. AI 편집은 어떻게 만들었을까요?

### 4.1 서버 → 상태 관리 → 화면 순서로 만들었습니다

AI 기능은 서버(`e1f758b`), 브라우저의 상태 관리(`0f83c0e`), 화면(`3e0436a`) 순서로 만들었습니다. 화면을 마지막에 둔 이유는, 요청 → 대기 → 스트리밍 → 검토 → 적용·버리기·중단이라는 상태 흐름을 먼저 테스트로 굳혀 두고 싶었기 때문입니다. 화면은 이 상태를 그리기만 하면 됩니다.

<br>

### 4.2 서버는 API 키를 지키고 중계만 합니다

이 앱에서 서버가 꼭 필요한 이유는 하나입니다. API 키를 브라우저에 보내지 않는 것입니다. 그래서 서버 기능은 [route.ts](../src/app/api/ai/edit/route.ts) 하나이고, 이 파일도 `lib/ai/server`를 부르는 얇은 어댑터입니다.

- 서버 전용 파일에는 `import "server-only"`를 붙였습니다. 브라우저 코드가 가져가면 빌드가 실패합니다.
- 요청은 zod로 검증하고, 서버가 허용한 모델로만 요청할 수 있습니다. 브라우저가 임의의 모델로 비용을 쓰지 못하게 하기 위해서입니다.
- 요청 크기 제한(`AI_LIMITS`)은 브라우저가 자를 때와 서버가 검증할 때 같은 값을 씁니다.

<br>

### 4.3 결과는 도구 호출로, 완성된 셀만 받습니다

AI가 쓴 글에서 셀 값을 찾아내는 대신, `{ cell, value }` 목록을 도구 호출(tool use)로 받았습니다. 형식이 확실하고, AI의 설명과 실제 편집이 나뉩니다. 도구 입력을 스트리밍으로 받으면 셀 제안을 하나씩 미리보기로 보여 줄 수 있습니다.

그런데 SDK가 주는 부분 JSON 해석은 중간에 끊긴 문자열도 받아들일 수 있습니다. 그러면 `"1250"`이 아니라 `"12"` 같은 덜 만들어진 값이 제안으로 보입니다. 그래서 [edit-stream-parser.ts](../src/lib/ai/server/edit-stream-parser.ts)를 직접 만들었습니다. 괄호 깊이를 세다가 배열 원소 하나가 닫혔을 때만 `JSON.parse`로 엄격하게 읽습니다.

브라우저와 서버 사이는 fetch 응답을 한 줄씩 읽는 방식(NDJSON)으로 정했습니다. 요청에 시트 내용을 실어야 해서 POST가 필요했는데, 브라우저 기본 스트리밍(EventSource)은 GET만 지원하기 때문입니다.

여기서 하나 더 고민한 것이 오류 전달입니다. 응답을 보내기 시작하면 HTTP 상태 코드를 바꿀 수 없습니다. 그래서 서버는 AI의 첫 응답을 받은 뒤에 응답을 시작합니다. 키 오류나 요청 한도처럼 시작 전에 실패하면 HTTP 상태로, 시작한 뒤에 실패하면 스트림 안의 이벤트로 알립니다.

<br>

### 4.4 가짜 API는 SDK의 fetch 자리에 넣었습니다

API 키 없이도 개발하고 테스트할 수 있어야 했습니다. 가장 쉬운 방법은 서버 함수 바깥에서 응답을 흉내 내는 것이지만, 그러면 SDK가 응답을 해석하고 오류를 분류하는 부분은 확인할 수 없습니다.

그래서 [mock-anthropic.ts](../src/lib/ai/server/mock-anthropic.ts)를 SDK가 네트워크 요청을 보내는 자리(fetch)에 넣었습니다. SDK 입장에서는 실제 API와 같은 응답을 받으므로, 서버 코드 전체가 실제와 같은 경로를 지납니다. 지시문에 `[느림]`, `[한도]`, `[거절]` 같은 표시를 붙이면 지연과 오류도 재현할 수 있습니다. [ai-controller.test.ts](../tests/unit/ai/ai-controller.test.ts#L272)는 컨트롤러 → fetch → route → SDK → 가짜 API 전 구간을 한 번에 지납니다.

<br>

### 4.5 AI 결과는 확인한 뒤에만 시트에 씁니다

결과를 만드는 동안에는 시트에 아무것도 쓰지 않고, 제안으로만 갖고 있습니다. 두 가지 이유입니다.

- 완성되지 않은 값이 다른 사용자 화면에 퍼지지 않습니다.
- 적용할 때 한 번에 쓰므로, 실행 취소 한 번으로 모두 되돌릴 수 있습니다. 적용 직전에 선택을 바뀔 범위로 옮겨 두어서, 되돌리면 그 범위로 돌아옵니다.

<br>

## 5. 가장 오래 고민한 지점: 공동 편집과 AI가 만날 때

### 5.1 문제를 세 가지 값으로 나눴습니다

AI가 결과를 만드는 사이에 다른 사용자가 같은 셀을 고칠 수 있습니다. 이 상황을 판단하려면 값 세 개가 필요했습니다.

- **요청 때 값**: AI에 보낸 그 순간의 값
- **현재 값**: 지금 문서에 있는 값
- **제안 값**: AI가 낸 값

판단은 [classifyCell](../src/lib/ai/coedit.ts#L19) 세 줄입니다. 제안이 현재 값과 같으면 `same`, 요청 때 값에서 바뀌지 않았으면 `clean`, 바뀌었으면 `conflict`입니다. 충돌한 셀은 기본으로 건너뜁니다.

왜 사람의 입력을 우선했을까요? AI 결과는 다시 요청하면 또 만들 수 있지만, 사람이 입력한 값은 한 번 사라지면 되살리기 어렵기 때문입니다.

<br>

### 5.2 판단 결과는 저장하지 않고 매번 다시 비교합니다

[states](../src/lib/ai/ai-controller.ts#L96)는 비교 결과를 들고 있지 않고, 부를 때마다 현재 값과 다시 비교합니다. 그래서 다른 사용자가 값을 원래대로 되돌리면 충돌도 저절로 풀립니다.

덮어쓰기를 골라도 "고를 때 본 값"에만 적용됩니다. 고른 뒤에 값이 또 바뀌었다면, 그건 내가 보지 못한 다른 사람의 새 값입니다. 그래서 다시 고를 때까지는 건너뜁니다.

<br>

### 5.3 판단과 쓰기 사이에 틈이 없게 했습니다

[apply](../src/lib/ai/ai-controller.ts#L167)는 세 가지를 한 번에 합니다.

1. 내가 입력 중이던 값을 먼저 확정합니다. 그 셀이 제안 대상이면 충돌로 판단됩니다.
2. 화면에 보이던 상태가 아니라 현재 값으로 다시 판단합니다.
3. 판단한 결과를 한 트랜잭션으로 씁니다.

2와 3이 같은 동기 코드 안에 있어서, 그 사이에 다른 탭의 메시지가 끼어들 수 없습니다. 다만 "탭 사이를 오가는 중인 메시지"까지는 막을 수 없습니다. 이 짧은 틈은 README의 "아직 남은 한계"에 적었고, 서버가 확인과 쓰기를 한 번에 처리해야 없앨 수 있습니다.

<br>

### 5.4 막을까요, 알릴까요?

다른 사용자가 AI로 편집 중인 범위를 내가 고치려고 할 때, 처음 떠오른 방법은 막는 것(hard lock)이었습니다. 하지만 기본은 알리기만 하는 것(soft lock)으로 정했습니다.

- 막으면 사람의 작업 흐름이 AI 때문에 끊깁니다.
- 확인 창으로 물으면 편집칸의 포커스를 빼앗아 한글 조합이 끊깁니다(2.2).
- 막지 않아도 5.1의 충돌 규칙이 사람의 입력을 지켜 줍니다.

그래서 입력을 시작하면 편집칸 위에 "○○님이 AI 결과 검토 중 · 입력한 값은 기본으로 유지돼요"만 띄웁니다. 겹치는 범위에 두 사람이 동시에 AI를 요청해도 막지 않습니다. 먼저 적용한 쪽의 변경이 나중 쪽에서 충돌로 보이기 때문입니다. 누가 먼저 상대의 표시를 봤는지에 결과가 좌우되지 않는다는 점이 이 방식의 장점이었습니다.

<br>

### 5.5 그래도 막아야 하는 경우를 위해 셀 잠금을 옵션으로 더했습니다

"검토하는 동안만큼은 아무도 건드리지 않았으면 좋겠다"는 경우도 있습니다. 그래서 툴바의 **AI 편집 시 셀 잠금**을 나중에 더했습니다(`d38b4a2`). 기본을 바꾸지 않고 옵션으로 둔 이유는 5.4와 같습니다.

잠금을 만들면서 정한 규칙은 이렇습니다.

- **잠근 실행은 요청한 범위를 그대로 알립니다.** 잠그지 않은 실행은 제안이 들어오는 대로 범위가 커지는데, 잠금 범위가 그렇게 바뀌면 어느 셀이 잠겼는지 예측할 수 없기 때문입니다([aiActivityOf](../src/lib/ai/coedit.ts#L82)).
- **잠긴 범위에는 AI 실행이 하나뿐입니다.** 남이 잠근 범위에는 요청할 수 없고, 다른 AI 편집과 겹치는 범위는 잠글 수 없습니다([blockingOverlaps](../src/lib/ai/coedit.ts#L116)).
- **막는 곳은 컨트롤러 한 곳입니다.** 입력 시작, 지우기, 서식 변경이 모두 [blockIfLocked](../src/lib/controller/sheet-controller.ts#L280)를 지납니다. 명령을 한 곳에 모아 두었기 때문에, 입력 경로가 다섯 개여도 막는 코드는 하나입니다.
- **잠기기 전부터 입력하던 값은 확정할 수 있습니다.** 이미 입력한 글자를 버리지 않기 위해서입니다. 그 셀은 5.1의 규칙대로 충돌로 표시됩니다.

잠금도 탭 사이 메시지로 전달되므로, 전달되기 전 아주 짧은 순간의 입력은 막지 못합니다. 그래서 잠금을 켜도 충돌 판단은 그대로 둡니다. 잠금은 충돌을 줄여 주는 장치이고, 마지막 안전장치는 여전히 충돌 판단입니다.

<br>

### 5.6 AI 제안은 다른 사람에게 보여 주지 않습니다

검토 중인 범위에는 색 점선과 "AI 결과 검토 중" 이름표만 보이고, 제안 값은 보이지 않습니다. 확정되지 않은 값이 실제 데이터처럼 보이면 혼란스럽기 때문입니다.

그런데 그다음 커밋(`2c03693`)에서 다른 사람이 **입력 중인 값**은 확정 전에도 보여 주기로 했습니다. 둘 다 "확정되지 않은 값"인데 왜 다르게 다룰까요? 고민한 끝에 이렇게 구분했습니다.

- 사람의 입력은 그 사람의 커서 테두리와 "입력 중" 이름표 안에 한 칸씩 나타나서, 실제 값과 쉽게 구분됩니다.
- AI 제안은 범위 전체에 한꺼번에 깔려서 실제 데이터처럼 보이기 쉽습니다. 토큰이 올 때마다 모든 탭에 값을 보내야 하는 부담도 있습니다.

<br>

### 5.7 입력 중인 값은 문서가 아니라 사용자 정보에 싣습니다

입력 중인 값을 문서(Y.Doc)에 쓰면 저장되고, 실행 취소 기록에도 남습니다. 그래서 커서와 같은 경로(awareness)로만 보냈습니다. 확정하기 전까지는 저장되지 않고, Esc로 취소하면 다른 화면에서도 원래 값으로 돌아갑니다.

한 글자마다 모든 탭에 보내기 때문에 1,000자까지만, 바뀌었을 때만 보냅니다([setDraft](../src/lib/collab/presence.ts#L85)). 다른 사용자가 입력 중인 값은 화면에 보이더라도 AI 충돌 판단에는 넣지 않습니다. 아직 확정되지 않은 값이기 때문입니다.

<br>

### 5.8 수식 입력줄도 같은 길을 지나게 했습니다

수식 입력줄에서 값을 고칠 수 있게 할 때(`53b0784`), 별도의 편집 경로를 만들지 않았습니다. [replaceDraft](../src/lib/controller/sheet-controller.ts#L178)가 수식 입력줄의 글자를 셀 편집칸에도 똑같이 써 넣습니다. 그래서 확정, 이동, 실행 취소, 잠금, 다른 사용자에게 보이는 방식이 셀에서 입력할 때와 같습니다.

두 칸 사이로 포커스를 옮길 때 편집이 확정되면 안 됐습니다. 그래서 두 칸에 같은 표시(`data-draft-input`)를 붙이고, 포커스가 표시가 붙은 칸 사이에서 옮겨 갈 때는 확정하지 않게 했습니다([draft-input.ts](../src/lib/sheet/draft-input.ts)).

<br>

## 6. 기능이 늘어난 뒤, 구조를 한 기준으로 맞췄습니다

### 6.1 왜 중간에 구조를 정리했을까요?

AI 기능까지 붙고 나니(10/4) 기능은 동작했지만, 코드가 한 기준으로 짜여 있지 않았습니다. 예를 들면 이런 것들입니다.

- hook이 컴포넌트 파일을 import하는 역방향 의존이 있었습니다(`viewport`).
- `coedit.ts`와 `ai-controller.ts`가 서로를 import하고 있었습니다.
- 서버가 화면 문구를 만들어 보내고 있었습니다.
- 가장 긴 className이 172자였고, 비슷한 색이 팔레트 이름으로 여러 가지 섞여 있었습니다.

새 기능(셀 잠금, 입력 중인 값 공유)을 더하기 전에 이걸 먼저 정리했습니다. 기준이 없는 상태에서 기능을 더하면, 파일마다 다른 방식이 계속 늘어나기 때문입니다.

<br>

### 6.2 구조 규칙을 문서로 남겼습니다

정리를 시작하면서 [SKILL.md](../.claude/skills/project-structure/SKILL.md)에 규칙부터 적었습니다(`4a94ac2`). 이 문서의 첫 문장이 정리의 방향입니다.

> 목표는 "더 잘게 쪼개기"가 아니라 **한 기준으로 일관되게 판단하기**다.

왜 문서로 남겼을까요? 파일을 나눌지 말지를 매번 감으로 정하면, 같은 상황에서 다른 결정이 나옵니다. 기준이 글로 있으면 사람도, Claude Code 같은 AI 도구도 같은 기준으로 판단할 수 있습니다. 그래서 Claude Code가 구조를 판단할 때 읽는 skill 형식으로 두었습니다.

규칙의 뼈대는 네 가지입니다.

- **import는 한 방향으로만 흐릅니다.** `app → components → hooks → lib`. `lib`에는 React가 없고, `lib` 안에서도 `sheet`는 `collab`과 `ai`를, `collab`은 `ai`를 모릅니다. 그래서 AI 기능을 빼도 시트와 공동 편집은 그대로 동작합니다.
- **파일을 나누는 기준이 있습니다.** 한 파일에서만 쓰고, 직접 데이터를 읽지 않고, 200줄 이하면 같은 파일에 둡니다. 하나라도 어기면 나눕니다. 부모와 자식이 함께 커지면 폴더로 묶고 `index.tsx`만 밖에 공개합니다.
- **데이터는 위에서 읽고 아래로 내립니다.** Context와 store 구독은 기능의 최상위 컴포넌트에서만 하고, 하위 컴포넌트는 props와 콜백만 받습니다.
- **"상태 → 무엇을 보여 줄지"는 순수 함수로 뺍니다.** 기능마다 `messages.ts`가 문구와 의미 값(`tone: "warn"`, `icon: "spinner"`)을 돌려주고, 컴포넌트는 그걸 마크업으로 바꾸기만 합니다.

규칙과 코드가 다르면 코드를 규칙에 맞추고, 규칙이 틀렸다면 문서를 먼저 고치기로 했습니다. 지킬 수 없는 경우는 "알려진 예외"에 이유와 함께 적었습니다. 예를 들어 `SheetContext.tsx`가 hook을 함께 내보내는 것은, hooks로 옮기면 hooks가 components를 import하게 되어서 지금은 그대로 둡니다(`a6062bf`).

<br>

### 6.3 서버는 코드만 보내고, 문구는 브라우저가 고릅니다

처음에는 서버가 오류 문구를 만들어 보냈습니다. 정리하면서 서버는 오류 코드(와 개수 같은 값)만 보내고, 화면 문구는 브라우저가 [strings.ts](../src/resources/strings.ts)에서 고르게 바꿨습니다(`345425f`). 문구는 한 파일에서만 고치면 되고, 서버는 화면을 몰라도 됩니다. 프로토콜에 문구가 실리지 않는지는 [messages.test.ts](../tests/unit/ai/messages.test.ts)에서 확인합니다.

<br>

### 6.4 공통 스타일은 만들었다가 일부를 되돌렸습니다

디자인 토큰과 공통 클래스를 처음 만들 때(`ffd53fb`)는 화면별로 클래스를 많이 만들었습니다. 그런데 다시 보니, 한 곳에서만 쓰는 클래스는 이름만 하나 더 생긴 것이었습니다. 그래서 다음 정리(`0309d15`)에서 여러 곳에서 쓰는 컨트롤(버튼, 칩, 배지, 안내 등)만 공통 클래스로 남기고, 나머지는 컴포넌트 안으로 되돌렸습니다.

대신 값의 단계는 강하게 묶었습니다. 글자 크기 6가지를 4단계로, 간격을 7단계로 맞추고, Tailwind 기본 팔레트를 꺼서 토큰 밖의 값은 클래스가 아예 만들어지지 않게 했습니다. 버튼의 눌림·선택 같은 상태는 클래스를 이어 붙이지 않고 `aria-pressed` 같은 속성으로 표현해서, 접근성과 스타일을 한 번에 맞췄습니다.

<br>

### 6.5 큰 컨트롤러는 "조율"만 남기고 나눴습니다

`AiController`와 `Presence`가 커지면서 책임을 나눴습니다(`734a13d`).

- AI 실행의 상태 변화(`applyProgress`, `finishRun`)와 요청 만들기는 순수 함수로 뺐습니다([run.ts](../src/lib/ai/run.ts), [request.ts](../src/lib/ai/request.ts)). 컨트롤러는 요청, 타이머, 알림을 조율하는 일만 맡습니다.
- 사용자 정보의 형식 검증은 [presence-state.ts](../src/lib/collab/presence-state.ts), 탭 생존 확인은 [liveness.ts](../src/lib/collab/liveness.ts), 이름·색 만들기는 [identity.ts](../src/lib/collab/identity.ts)로 나눴습니다.

<br>

## 7. 마지막으로, 이름만 보고 읽히게 다듬었습니다

10/8에는 동작을 바꾸지 않고, 코드를 처음 읽는 사람이 이름만 보고 동작을 알 수 있게 다듬었습니다. 이 과정에서 실제 버그도 하나 찾았습니다.

**이름이 숨긴 동작이 버그를 만들었습니다**

`AiController`의 `settle`은 이름과 달리 타이머 정리와 함께 진행 중인 요청(`inflight`)도 비우고 있었습니다. 그래서 `destroy`가 그 뒤에 부르던 `abort`가 실행되지 않았고, 패널을 닫아도 진행 중인 요청이 끊기지 않았습니다. 이를 `endRequest`와 `stopWatchdog`으로 나눠 이름에 동작을 드러내고, 요청을 끊을지는 부르는 쪽이 정하게 고쳤습니다(`75a78f3`).

**그 밖에 다듬은 것**

- 한 타입 안에서 두 뜻으로 쓰이던 `skipped`를 "범위 밖이라 받지 않은 제안"(`excluded`)과 "충돌로 건너뛴 셀"(`skipped`)로 나눴습니다(`aadc246`).
- `startEdit(mode, true)`처럼 호출하는 곳에서 뜻이 보이지 않던 boolean 인자를 `{ keepContent: true }`나 상태 값으로 바꿨습니다(`94f8b3e`, `79f5edf`).
- 여섯 곳에 있던 `status === "review"`를 `isReviewing`으로, 아홉 곳에 있던 "범위를 시트 안으로 자르기"를 `clipToSheet`로 모았습니다(`c7b9419`, `16608a4`).
- 툴바 안내와 키 판정이 단축키를 따로 적고 있어서, 단축키를 바꾸면 안내가 틀린 채로 남을 수 있었습니다. [keymap.ts](../src/lib/sheet/keymap.ts) 한 곳에서 정의하게 했습니다(`958d8e6`).
- 모델 하나를 추가하려면 네 곳을 고쳐야 했고, 빠뜨려도 알 수 없었습니다. 모델 목록에서 타입을 뽑아, 설명이나 지원 옵션이 빠지면 타입 오류가 나게 했습니다(`25fae8e`).
- 주석은 코드를 되풀이하는 것을 지우고, 브라우저 제약이나 공동 편집 규칙처럼 "왜"가 필요한 것만 남겼습니다(`9934422`).
- import 순서는 ESLint(`import/order`)로 검사합니다(`bbc53a4`).

## 8. 테스트는 어떻게 했을까요?

### 8.1 화면 없이, 실제 탭처럼 돌립니다

로직이 모인 `lib`에 React가 없어서, 테스트가 모두 Node에서 돕니다. 처음 계획은 Playwright로 여러 탭을 띄우는 것이었지만, Node에도 BroadcastChannel과 Web Locks가 있다는 점을 이용했습니다. 테스트 안에서 실제 세션을 여러 개 열면 브라우저 탭 여러 개와 같은 경로로 동작합니다. IndexedDB는 가짜 구현(fake-indexeddb)으로 대신합니다.

README의 "공동 편집과 AI가 만나는 지점" 세 상황도 [coedit-tabs.test.ts](../tests/unit/ai/coedit-tabs.test.ts)에서 세션 두 개로 그대로 재현합니다.

<br>

### 8.2 바깥에서 넣을 수 있게 만들었습니다

- AI 전송은 `AiTransport` 함수로 받습니다. 실제로는 fetch, 테스트에서는 원하는 이벤트를 원하는 순간에 흘려보내는 가짜입니다.
- 화면 조작은 `SheetView` 인터페이스로 받습니다. 그래서 컨트롤러를 화면 없이 테스트할 수 있습니다.
- 시간 기준값(`SLOW_AFTER_MS`, `IDLE_TIMEOUT_MS`, `STORAGE_TIMEOUT_MS`)을 밖으로 꺼내 두어서, 가짜 타이머로 정확히 그만큼 앞당겨 확인합니다.

<br>

### 8.3 가끔 실패하던 테스트에서 배운 것

다른 탭 좌표를 확인하는 테스트가 가끔 실패했습니다(`e14e89d`). 원인은 3.2의 색 충돌 규칙이었습니다. 두 탭이 같은 색으로 열리면, 번호에 따라 한 탭이 나중에 색을 바꾸면서 테스트가 직접 넣은 상태를 덮어썼습니다. 테스트가 공동 편집 규칙을 피해 가지 않고, 규칙 위에서 돌고 있다는 것을 보여 준 경우였습니다.

<br>

## 10. 아직 남은 고민

남은 한계는 대부분 "탭 사이 메시지가 오가는 짧은 틈"에서 생깁니다. 같은 셀의 동시 확정, AI 적용 순간의 변경, 잠금이 전달되기 전의 입력이 그렇습니다. 같은 브라우저 안에서는 이 틈이 수 밀리초지만, 실제 네트워크에서는 수백 밀리초로 늘어납니다.

그래서 네트워크로 넓힐 때는 "서버가 순서를 정한다"는 방향으로 정리했습니다. 원본, 연결 끊김, 사용자 이름, 셀 잠금, AI 적용 확인을 서버가 맡고, 화면에서 먼저 막는 지금 구조는 그대로 둡니다. 자세한 내용은 README의 "4. 아직 남은 한계"와 "5. 공동 편집 구조를 실제 네트워크 기반 동기화로 확장한다면"에 있습니다.
