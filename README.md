# spread-sheet

여러 사람이 동시에 편집하고, AI의 도움도 받을 수 있는 웹 스프레드시트입니다.

<br>

## 실행 방법

Node.js 20 이상이 필요합니다.

```bash
npm install
cp .env.example .env.local
```

복사한 `.env.local`에서 `ANTHROPIC_API_KEY`만 채우면 됩니다. 나머지 값은 기본값 그대로 두어도 됩니다.

```bash
# .env.local
ANTHROPIC_API_KEY=${key}
# 사용할 모델 (기본값: claude-opus-5-5). 예: claude-sonnet-5-5, claude-haiku-4-5
ANTHROPIC_MODEL=claude-opus-5-5
# 생각하는 정도: low | medium | high (기본값: low, 빠른 응답 우선)
ANTHROPIC_EFFORT=low
# 1로 두면 API 키가 있어도 가짜 응답으로 동작합니다(지연·오류 재현용).
AI_MOCK=
```

API 키를 비워 두면 가짜 Claude API로 동작합니다. 키 없이도 AI 편집 흐름을 그대로 확인할 수 있습니다.

키를 채웠으면 개발 서버를 켭니다.

```bash
npm run dev
```

브라우저에서 http://localhost:3000 을 엽니다. 같은 주소를 탭 여러 개로 열면, 탭마다 서로 다른 사용자가 됩니다.

<br>

## 1. 공동 편집

### 1.1 다른 사용자가 무엇을 하고 있는지 보입니다

다른 사용자의 선택 범위와 커서는 그 사람의 색 테두리와 이름표로 보입니다. 참여자 목록에는 "B2 입력 중", "A1:C3 보는 중" 같은 상태가 나옵니다.

<br>

### 1.2 입력 중인 값도 바로 보입니다

다른 사용자가 셀에 입력하면, 확정하기 전이라도 그 셀에 글자가 실시간으로 나타납니다. 이름표에는 "입력 중"이 붙습니다. 한글을 조합하는 중인 글자, F2나 더블클릭으로 고치는 중인 기존 값도 똑같이 보입니다.

입력 중인 값은 문서에 쓰지 않습니다. 커서와 같은 경로(awareness)로만 보냅니다. 그래서 확정하기 전까지는 저장되지 않고, 실행 취소 기록에도 남지 않습니다. 입력하던 사람이 Esc로 취소하면 다른 화면에서도 원래 값으로 돌아갑니다.

<br>

### 1.3 같은 셀을 동시에 고치면, 나중에 확정한 값이 남습니다

두 사람의 입력을 글자 단위로 섞지 않습니다. 셀 값은 "100"과 "200"이 섞이면 아무 의미 없는 값이 되기 때문입니다. Google Sheets도 같은 방식을 씁니다.

대신 같은 셀을 동시에 입력하면 편집칸 위에 "○○님도 이 셀을 입력 중이에요"를 띄워서, 서로 알아챌 수 있게 했습니다.

셀 값은 셀마다 객체를 따로 두지 않고 "B2" 같은 평평한(flat) 키로 저장합니다. 빈 셀에 두 사람이 동시에 처음 입력해도 두 변경이 모두 남게 하기 위해서입니다.

<br>

### 1.4 탭을 닫으면 바로 사라집니다

탭이 닫히면 Web Locks로 즉시 알아챕니다. 그 사용자의 커서, 입력 중인 값, AI 편집 표시가 다른 화면에서 바로 사라집니다.

<br>

## 2. 공동 편집과 AI가 만나는 지점

### 2.1 AI가 결과를 만드는 동안 누가 그 셀을 고치면 어떻게 될까요?

AI에 편집을 요청하면 그 순간의 셀 값(이하 **요청 때 값**)을 함께 보냅니다. 그런데 AI가 결과를 만드는 사이에 다른 사용자가 같은 셀을 고칠 수 있습니다. 이때 AI 결과가 사람의 입력을 몰래 덮어쓰면 안 됩니다. 그래서 아래처럼 처리합니다.

**셀 잠금을 끈 경우 (기본)**

- AI 생성은 멈추지 않고 계속 진행합니다.
- 미리보기는 요청 때 값이 아니라, 항상 **현재 값**과 비교해서 보여 줍니다.
- 요청 때 값과 현재 값이 달라진 셀은 **충돌**로 표시합니다.
  - 시트에서는 현재 값을 가리지 않도록 주황 테두리만 두릅니다.
  - AI 패널에서는 "요청 때 값 → 현재 값"과 AI 제안 값을 나란히 보여 줍니다.
- 충돌한 셀은 기본으로 **적용하지 않고 건너뜁니다.**
  - 필요하면 셀마다, 또는 한 번에 덮어쓰기를 고를 수 있습니다.
  - **지금 값으로 다시 요청**을 누르면, 같은 요청을 최신 시트 기준으로 다시 보냅니다.
- 셀을 지운 것도 "빈칸으로 바뀐 것"으로 보고 같은 규칙을 따릅니다. 행·열 삽입 기능이 없어서 셀 주소가 밀리는 문제는 없습니다.
- AI 결과를 적용할 때 내가 입력 중이던 값이 있으면, 먼저 확정한 뒤 같은 규칙으로 판단합니다.
- 다른 사용자가 **입력 중인 값**은 화면에 보이더라도 충돌로 보지 않습니다. 아직 확정되지 않은 값이기 때문입니다.
  - 그 사용자가 내 적용보다 먼저 확정하면, 충돌로 표시되어 건너뜁니다.
  - 내 적용보다 나중에 확정하면, 그 값이 AI 값을 덮어씁니다.
  - 어느 쪽이든 사람이 입력한 값이 남습니다.

왜 사람의 입력을 우선했을까요? AI 결과는 다시 요청하면 또 만들 수 있지만, 사람이 입력한 값은 한 번 사라지면 되살리기 어렵기 때문입니다.

**셀 잠금을 켠 경우**

툴바의 **AI 편집 시 셀 잠금**을 켜고 요청하면, AI 생성부터 적용·버리기까지 다른 사용자는 요청한 범위의 셀을 바꿀 수 없습니다. 입력 시작, 지우기, 서식 변경이 모두 막힙니다. 그래서 위와 같은 충돌이 원칙적으로 생기지 않고, AI 제안을 그대로 적용할 수 있습니다.

다만 아래 경우에는 잠금을 켜도 셀 값이 바뀔 수 있습니다. 이때는 기본 동작과 같은 규칙으로 처리합니다.

- 잠기기 전부터 입력하던 값을 확정한 경우
- 잠금이 다른 탭에 전달되기 전, 아주 짧은 순간에 입력한 경우
- 다른 사용자가 잠기기 전에 한 자신의 편집을 실행 취소한 경우

잠긴 셀이 다른 사용자에게 어떻게 보이는지는 2.2에서 이어서 설명합니다.

<br>

### 2.2 한 사람이 AI 결과를 검토하는 동안, 다른 사용자에게는 무엇이 보일까요?

검토 중인 범위에는 검토하는 사람의 색 점선과 "○○ · AI 결과 검토 중" 이름표가 보입니다. 아직 생성 중이라면 "AI 편집 중"으로 보입니다. 참여자 목록에도 같은 상태가 나옵니다.

**AI의 제안 값은 보여 주지 않습니다**

확정되지 않은 값이 실제 데이터처럼 보이면 혼란스러울 것이라고 판단했습니다.

사람이 입력 중인 값은 보여 주는데, AI 제안은 왜 다르게 다룰까요? 사람의 입력은 그 사람의 커서 테두리와 "입력 중" 이름표 안에 한 칸씩 나타나서, 실제 값과 쉽게 구분됩니다. 반면 AI 제안은 범위 전체에 한꺼번에 깔려서 실제 데이터처럼 보이기 쉽습니다. 토큰이 올 때마다 모든 탭에 값을 보내야 하는 부담도 있습니다.

**기본으로는 막지 않고 알리기만 합니다 (soft lock)**

다른 사용자가 AI로 편집하거나 검토 중인 범위라도, 내가 편집하는 것은 막지 않습니다. 대신 입력을 시작하면 편집칸 위에 "○○님이 AI 결과 검토 중 · 입력한 값은 기본으로 유지돼요"를 띄웁니다.

- 기본을 하드 락(hard lock)으로 두지 않은 이유: 사람의 작업 흐름이 AI 때문에 끊기기 때문입니다.
- 확인 창으로 묻지 않는 이유: 확인 창이 편집칸의 포커스를 빼앗으면 한글 조합이 중간에 끊기기 때문입니다.

**셀 잠금을 켜면 막습니다 (hard lock)**

툴바의 **AI 편집 시 셀 잠금**을 켜고 요청하면, 결과를 적용하거나 버릴 때까지 요청한 범위를 다른 사용자가 바꿀 수 없습니다. 시트 전체로 요청했다면 시트 전체가 잠깁니다.

- 잠긴 셀에서 입력을 시작하거나, 지우거나, 서식을 바꾸려고 하면 막히고 "○○님이 AI 편집을 위해 잠근 셀이에요"가 뜹니다.
- 이름표와 참여자 목록에는 "· 잠금"이 붙습니다.
- 잠기기 전부터 입력하던 값은 확정할 수 있습니다. 이미 입력한 글자를 버리지 않기 위해서입니다. 그 셀은 2.1의 규칙대로 충돌로 표시됩니다.
- 잠금은 토글을 켠 뒤의 다음 요청부터 적용됩니다. 요청할 때 정해진 범위는 실행이 끝날 때까지 바뀌지 않습니다.

검토하던 탭이 닫히면 Web Locks로 즉시 알아채서 표시와 잠금이 함께 사라집니다. 그래서 탭이 비정상적으로 종료되어도 잠금이 남지 않습니다.

<br>

### 2.3 두 사람이 겹치는 범위에 동시에 AI 편집을 요청하면 어떻게 될까요?

보내기 전에 요청창 위에 "○○님이 이 범위를 AI로 편집 중이에요"가 뜹니다. 그래도 요청은 막지 않습니다.

먼저 적용한 쪽의 변경은, 나중에 적용하는 쪽에게 2.1의 규칙대로 충돌로 표시되고 기본으로 건너뜁니다. 두 AI가 같은 값을 냈다면 충돌이 아닙니다.

잠금이 없으니 서로 기다리다 멈추는 일도 없습니다. 거의 동시에 눌러서 서로의 표시를 못 본 경우에도 같은 규칙으로 처리됩니다. 누가 먼저 봤는지에 결과가 좌우되지 않습니다.

셀 잠금을 쓸 때는 예외입니다. 다른 사람이 잠근 범위에는 요청할 수 없고, 다른 AI 편집과 겹치는 범위는 잠글 수 없습니다. 그래서 잠긴 범위에는 언제나 AI 실행이 하나뿐입니다.

<br>

## 3. 주요 의사 결정 사항

여기서는 기능별로 코드를 왜 이런 구조로 만들었는지 정리합니다.

<br>

### 3.1 로직은 화면 밖에 둡니다

화면(React) 코드와 로직을 나눴습니다. import는 `app → components → hooks → lib` 한 방향으로만 흐르고, 로직이 모인 `lib`에는 React가 없습니다.

이렇게 나누면 핵심 로직을 브라우저 없이 테스트할 수 있습니다. 화면을 바꿔도 로직은 그대로 둘 수 있습니다. `lib` 안에서도 시트(`sheet`)는 공동 편집(`collab`)과 AI(`ai`)를 모르게 했습니다. 그래서 AI 기능을 빼도 시트와 공동 편집은 그대로 동작합니다.

**명령은 컨트롤러 한 곳에 모았습니다**

키보드, 마우스, 툴바, 수식 입력줄, AI 패널은 모두 `SheetController`의 같은 명령을 부릅니다. 입력 경로가 다섯 가지여도 "편집 중이면 먼저 확정한다", "잠긴 셀이면 막는다" 같은 규칙은 한 곳에만 있으면 됩니다. 스크롤이나 포커스처럼 DOM이 필요한 일은 그리드가 대신 맡아 줍니다. 그래서 컨트롤러는 화면 없이도 테스트할 수 있습니다.

**상태 관리 라이브러리는 쓰지 않았습니다**

키를 누르는 순간에는 다음 화면이 그려지기를 기다리지 않고, 최신 선택 위치를 바로 읽어야 합니다. 필요한 기능은 값 읽기, 값 바꾸기, 바뀌면 알리기 세 가지뿐이었습니다. 그래서 24줄짜리 저장소(`Store`)를 직접 만들고, 화면은 React 표준 방식(`useSyncExternalStore`)으로 구독만 하게 했습니다.

**화면 문구는 한 파일에 모았습니다**

모든 문구는 `resources/strings.ts`에 있습니다. "어떤 상태일 때 어떤 문구를 보여 줄지"는 기능마다 `messages.ts`의 함수가 정합니다. 색이나 아이콘도 `"warn"`, `"spinner"` 같은 뜻만 돌려주고, 실제 모양은 컴포넌트가 정합니다. 이렇게 하면 문구를 바꿀 때 로직을 건드리지 않아도 되고, 판단 로직은 화면 없이 테스트할 수 있습니다.

**구조 규칙은 문서로 남겼습니다**

파일을 나누는 기준, import 방향, 로직을 둘 위치를 `.claude/skills/project-structure/SKILL.md`에 적고, 이 기준에 맞춰 코드를 정리했습니다. import 순서는 ESLint로 검사합니다.

<br>

### 3.2 셀 데이터의 원본은 하나뿐입니다

**Yjs(CRDT)를 썼습니다**

CRDT는 순서를 정해 주는 서버가 없어도, 같은 변경을 받기만 하면 모든 탭이 같은 상태가 되는 데이터 구조입니다. 서버 없이 탭끼리 맞춰야 하는 이 프로젝트에 맞았습니다. Yjs에는 사용자 정보를 주고받는 기능(awareness)과, 변경의 출처별로 실행 취소하는 기능(UndoManager)도 함께 있어서 따로 만들 필요가 없었습니다.

**화면은 셀 값을 복사해 두지 않습니다**

화면은 "문서가 바뀌었다"는 신호만 받고, 그릴 때마다 문서(Y.Doc)에서 직접 값을 읽습니다. 원본이 하나뿐이라 원본과 복사본이 어긋날 일이 없습니다.

**모든 변경에 출처를 붙입니다**

셀을 바꾸는 코드는 모두 `document.ts`를 거칩니다. 이때 변경마다 출처(origin)를 붙입니다. 사람이 고쳤으면 `"user-edit"`, AI 결과를 적용했으면 `"ai-apply"`입니다. 실행 취소는 이 출처만 보고 대상을 고릅니다. 다른 탭에서 온 변경에는 이 출처가 붙지 않아서, 내 실행 취소가 다른 사람의 입력을 지우지 않습니다.

값이 그대로인 셀은 아예 쓰지 않습니다. 그래서 실행 취소 기록에 아무것도 바뀌지 않은 단계가 생기지 않습니다.

**규칙은 한 곳에 둡니다**

- 시트 크기, 서식 종류, 숫자 판정, 주소·색 검증은 `schema.ts`에 있습니다. 화면, AI 프롬프트, 서버의 요청 검증이 같은 규칙을 씁니다.
- 값과 서식은 따로 저장합니다. AI에 보낼 셀 목록을 만들거나 Delete로 값만 지울 때 서식을 걸러낼 필요가 없습니다.
- 셀 주소는 두 가지 모양으로 다룹니다. 저장·전송·화면에는 사람이 읽는 `"B2"` 표기를, 선택·이동·위치 계산에는 0부터 세는 `{ row, col }`을 씁니다. 둘 사이 변환은 `address.ts`가 맡습니다.

<br>

### 3.3 탭끼리 맞추고, 브라우저에 저장합니다

**문서, 저장, 전송을 따로 조립합니다**

`session.ts`가 문서 하나에 IndexedDB 저장 부품과 탭 간 전송 부품을 각각 붙입니다. 그래서 저장이나 전송 방식을 바꿔도 문서와 화면은 바뀌지 않습니다. 아래에서 네트워크 동기화로 확장할 때 바꿀 곳이 이 파일에 모인다고 한 이유입니다.

**받은 변경은 다시 보내지 않습니다**

다른 탭에서 받은 변경을 다시 보내면, 탭끼리 같은 변경을 끝없이 주고받게 됩니다. 사용자 정보도 자기 것만 보냅니다. 다른 탭의 정보를 대신 보내면, 이미 떠난 사용자가 되살아나서 목록이 깜빡이기 때문입니다.

**저장된 내용을 다 불러온 뒤에 시트를 보여 줍니다**

빈 시트가 잠깐 보였다가 내용이 채워지면 어색하기 때문입니다.

그런데 IndexedDB 라이브러리(y-indexeddb)는 불러오기에 성공했을 때만 알려 주고, 실패는 알려 주지 않습니다. 성공만 기다리면, 저장소가 막힌 브라우저에서는 로딩 화면이 끝나지 않습니다. 그래서 불러오기 성공, 저장소 열기 실패, 5초 경과 중 먼저 오는 것으로 결정합니다. 저장소를 열지 못해도 탭 간 동기화는 그대로 되고, 경고만 띄웁니다.

**실행 취소는 동작 하나가 한 단계입니다**

Yjs는 기본으로 0.5초 안에 이어진 편집을 한 단계로 합칩니다. 이 간격을 0으로 바꿨습니다. 그래서 AI 결과처럼 한 번에 쓴 변경은 정확히 한 단계가 됩니다. 되돌릴 때는 그 변경이 있던 곳으로 선택 위치도 함께 돌아갑니다.

<br>

### 3.4 다른 사용자의 정보는 들어오는 곳에서 한 번만 확인합니다

- **사용자 이름과 색은 탭마다 저장합니다.** sessionStorage는 탭마다 따로 있습니다. 그래서 새 탭은 새 사용자가 되고, 같은 탭을 새로고침하면 같은 이름으로 돌아옵니다.
- **이름이나 색이 겹치면 번호가 큰 쪽이 양보합니다.** 탭마다 붙는 번호(clientID)를 비교합니다. 서로 묻지 않아도 양쪽이 같은 규칙을 따르므로 한쪽만 바뀝니다. 탭을 복제해서 이름이 그대로 복사된 경우도 이 규칙으로 풀립니다.
- **다른 탭에서 온 값은 받자마자 확인하고 맞춥니다.** 다른 탭은 이전 버전의 코드로 돌고 있을 수도 있습니다. 그래서 형식을 먼저 확인하고(`isPresenceState`), 좌표를 시트 안으로 맞춘 뒤(`normalizePresenceState`) 참여자 목록에 넣습니다. 목록을 쓰는 화면은 좌표를 다시 확인하지 않아도 됩니다.
- **입력 중인 글자는 1,000자까지만, 바뀌었을 때만 보냅니다.** 한 글자마다 모든 탭에 보내기 때문에 크기를 제한했습니다.

<br>

### 3.5 한글 입력이 깨지지 않게 만들었습니다

**보이지 않는 편집칸이 늘 셀 위에 있습니다**

편집을 시작하면서 포커스를 다른 칸으로 옮기면, 한글 조합이 끊기고 첫 자모가 사라집니다. 그래서 투명한 편집칸이 항상 선택한 셀 위에서 포커스를 갖고 있게 했습니다. 셀을 선택하고 바로 타이핑해도 조합이 같은 칸에서 시작되고, 입력기 후보창도 셀 위치에 뜹니다.

**편집칸의 값은 React가 관리하지 않습니다**

React가 화면을 그릴 때마다 편집칸 값을 덮어쓰면, 조합 중인 글자가 깨집니다. 그래서 입력 중인 글자는 편집칸(DOM)이 직접 들고 있고, 필요할 때만 컨트롤러가 읽고 씁니다(비제어 input).

**조합 중에 누른 키는 시트가 처리하지 않습니다**

글자를 확정하려고 누른 Enter를 셀 이동으로 처리하면, 마지막 글자가 사라지거나 두 번 들어가기 때문입니다.

**키 처리는 세 단계로 나눴습니다**

"어떤 키인지 → 어떤 동작인지 → 어떤 명령을 실행할지"를 나눴습니다. 앞의 두 단계(`resolveGridKey`, `applyNavigation`)는 입력만 있으면 결과가 정해지는 함수입니다. 그래서 Tab 다음 Enter, Ctrl+방향키 같은 엑셀 규칙을 화면 없이 테스트할 수 있습니다. 단축키도 `keymap.ts` 한 곳에서 정의하고, 툴바의 안내 문구도 같은 정의를 읽습니다.

**수식 입력줄도 같은 길을 지납니다**

수식 입력줄에서 고친 글자는 컨트롤러를 거쳐 셀 편집칸에도 똑같이 들어갑니다. 그래서 확정, 이동, 실행 취소, 다른 사용자에게 보이는 방식이 셀에서 입력할 때와 같습니다. 두 칸 사이로 포커스를 옮길 때는 편집을 확정하지 않습니다.

<br>

### 3.6 그리드는 직접 만들었습니다

다른 사용자의 커서와 AI 미리보기를 셀 위에 겹쳐 그리고, 한글 입력을 세밀하게 다뤄야 했습니다. 기존 스프레드시트 라이브러리로는 이 부분을 바꾸기 어렵고, 라이선스 문제도 있었습니다.

- **셀 2,600개를 그대로 그리고, 다시 그리는 범위를 줄였습니다.** 시트 크기가 100×26으로 정해져 있어서, 보이는 셀만 그리는 기법(가상 스크롤)이 없어도 충분했습니다. 셀 전체는 문서가 바뀔 때만 다시 그리고, 그때도 실제로 내용이 바뀐 셀만 화면이 갱신됩니다.
- **겹쳐 그리는 순서를 정해 두었습니다.** 다른 사용자의 커서는 내 선택보다 아래에 두어, 내 커서가 가려지지 않게 했습니다. 이름표는 위에 두어 이름이 가려지지 않게 했습니다. 이 순서는 `layers.ts` 한 곳에 있습니다.

<br>

### 3.7 AI 결과는 확인한 뒤에만 시트에 씁니다

**AI 결과는 먼저 제안으로만 갖고 있습니다**

적용 버튼을 누를 때 한 번에 쓰므로, 실행 취소 한 번으로 모두 되돌릴 수 있습니다. 결과를 만드는 동안에는 시트에 아무것도 쓰지 않습니다. 그래서 완성되지 않은 값이 다른 사용자 화면에 퍼지지 않습니다.

**결과는 도구 호출로 받습니다**

AI가 쓴 글에서 셀 값을 찾아내는 대신, `{ cell, value }` 형식으로 받도록 했습니다(도구 호출). 형식이 확실하고, AI의 설명과 실제 편집이 나뉩니다. 이 값이 만들어지는 대로 도착하도록 스트리밍으로 받아서, 셀 제안을 하나씩 보여 줄 수 있습니다.

**도구 입력을 읽는 코드는 직접 만들었습니다**

왜 SDK가 제공하는 기능을 쓰지 않았을까요? SDK는 중간에 끊긴 문자열도 그대로 받아들일 수 있습니다. 그러면 `"1250"`이 아니라 `"12"` 같은 덜 만들어진 값이 제안으로 보입니다. 그래서 셀 하나의 값이 완전히 도착했을 때만 읽도록 했습니다.

**서버와는 스트림으로, 오류는 코드로 주고받습니다**

- 요청에 시트 내용을 담아야 해서 POST가 필요했습니다. 브라우저의 기본 스트리밍 방식(EventSource)은 GET만 지원해서, fetch로 응답을 한 줄씩 읽는 방식(NDJSON)을 택했습니다. 중간에 요청을 끊을 수도 있습니다.
- 서버는 AI의 첫 응답을 받은 뒤에 브라우저로 응답을 보내기 시작합니다. 응답을 보내기 시작하면 HTTP 상태 코드를 바꿀 수 없기 때문입니다. 그래서 키 오류나 요청 한도처럼 시작 전에 실패하면 HTTP 상태로, 시작한 뒤에 실패하면 스트림 안에서 알립니다.
- 서버는 오류 코드만 보내고, 화면에 보일 문구는 브라우저가 고릅니다. 문구를 한 곳에서만 고치면 되고, 서버는 화면을 몰라도 됩니다.
- 응답이 5초 동안 없으면 "응답 지연"을 표시하고, 60초가 지나면 시간 초과로 끝냅니다.

**API 키와 비용은 서버가 지킵니다**

- API 키는 서버 파일에서만 읽습니다. 서버 전용 파일에는 `import "server-only"`를 붙여, 브라우저 코드가 가져가면 빌드가 실패하게 했습니다.
- 요청은 zod로 검증하고, 서버가 허용한 모델로만 요청할 수 있게 했습니다.
- 요청 크기 제한은 브라우저가 보낼 때와 서버가 검증할 때 같은 값(`AI_LIMITS`)을 씁니다.

**API 키 없이도 같은 경로로 테스트할 수 있습니다**

가짜 Claude API를 SDK가 네트워크 요청을 보내는 자리(fetch)에 넣었습니다. SDK 바깥에서 흉내만 내면, SDK가 응답을 해석하고 오류를 처리하는 부분은 확인할 수 없기 때문입니다. 이렇게 하면 서버 코드 전체가 실제와 같은 경로를 지나고, 응답 지연·요청 한도·거절 같은 실패도 재현할 수 있습니다.

<br>

### 3.8 테스트는 화면 없이 실제 탭처럼 돌립니다

- 단위 테스트 236개가 모두 Node에서 돕니다. 로직(`lib`)에 React가 없기 때문에 가능합니다.
- 여러 탭은 실제 세션을 여러 개 열어 재현합니다. Node에도 탭 간 통신(BroadcastChannel)과 Web Locks가 있고, IndexedDB는 가짜 구현(fake-indexeddb)으로 대신합니다. 위에서 설명한 공동 편집과 AI가 만나는 세 상황도 세션 두 개로 그대로 재현해 검증합니다.
- AI 전송, 화면 조작, 무작위 값을 바깥에서 넣을 수 있게 만들었습니다. 시간 기준값도 밖으로 꺼내 두어서, 가짜 타이머로 정확히 그 시간만큼 앞당겨 확인합니다.

<br>

## 4. 아직 남은 한계

- 같은 셀을 두 사람이 동시에 확정하면, 먼저 확정한 값은 사라집니다. 서로 입력하는 모습과 안내는 보이지만, 막지는 않습니다.
- AI 결과를 적용하는 것과 거의 같은 순간(탭 사이에 메시지가 전달되는 짧은 시간)에 다른 탭에서 같은 셀을 고치면, CRDT 규칙에 따라 모든 탭이 두 값 중 하나로 똑같이 맞춰집니다. 이 짧은 틈까지 막으려면 서버가 순서를 정해 줘야 합니다.
- 셀 잠금도 탭 사이 메시지로 알리기 때문에, 잠금이 전달되기 전의 아주 짧은 순간에 한 입력은 막지 못합니다. 이 입력은 충돌로 처리됩니다.
- 셀 잠금은 실행 취소·다시 실행은 막지 않습니다. 잠기기 전에 그 셀에 한 편집을 되돌리면 값이 바뀌고, AI 결과에서 충돌로 표시됩니다.
- 검토 중인 제안은 그 탭에만 있습니다. 새로고침하면 사라져서 다시 요청해야 합니다.

<br>

## 5. 공동 편집 구조를 실제 네트워크 기반 동기화로 확장한다면

지금은 같은 브라우저의 탭끼리만 동기화합니다. 다음은 실제 네트워크 기반으로 다른 기기와도 함께 편집하려면 무엇을 바꿔야 할지 정리한 내용입니다.

<br>

### 문서를 맞추는 부분은 거의 그대로 쓸 수 있습니다

탭끼리 주고받는 메시지는 이미 y-websocket과 같은 형식(y-protocols)입니다. 그래서 문서를 맞추는 부분은 `BroadcastChannelProvider`를 `WebsocketProvider`로 바꾸면 됩니다.

- 셀 값을 평평한 키로 저장하는 방식, 실행 취소, AI 충돌 판단 규칙은 전송 방법과 상관없이 그대로 동작합니다.
- 다른 탭에서 온 상태를 검증하는 코드도 그대로 씁니다.
- 이 부품들은 `session.ts` 한 곳에서 조립합니다. 그래서 바꿀 곳도 여기에 모입니다.

<br>

### 5.1 원본은 서버에 둡니다

지금은 탭마다 IndexedDB에 저장하기 때문에 원본이라는 개념이 없습니다. 실제 네트워크 환경에서는 서버가 원본을 갖고, IndexedDB는 오프라인일 때 쓰는 임시 저장소로 사용합니다.

서버에서 시트를 지웠는데 과거 내용을 저장해 둔 사용자가 접속하면, CRDT가 두 내용을 합치면서 지운 내용이 되살아납니다. 그래서 문서마다 버전을 두고, 버전이 다르면 저장해 둔 내용을 버리게 해야 합니다.

<br>

### 5.2 접속이 끊긴 사람은 서버가 인식합니다

지금은 Web Locks로 탭이 닫힌 것을 인식합니다. 하지만 Web Locks는 같은 브라우저 안에서만 동작하기 때문에 수정이 필요합니다.

네트워크에서는 서버가 연결이 끊긴 것을 보고, 그 사람의 커서·입력 중인 값·AI 편집 표시를 지운 뒤 다른 사람에게 알립니다. 실제 사용에서는 잠깐 끊기는 일이 흔하기 때문에, 몇 초 기다렸다가 지워야 참여자 목록이 깜빡이지 않습니다.

<br>

### 5.3 사용자 이름은 서버가 정합니다

지금은 탭이 스스로 이름과 색을 정합니다. 네트워크에서 이렇게 두면 누구나 남의 이름을 쓸 수 있습니다. 그래서 서버가 로그인 정보로 이름을 채워 넣어야 합니다.

- 열람 권한만 있는 사람이 보낸 변경은 서버가 폐기합니다.
- 한 사람이 탭을 여러 개 열 수 있으므로, 참여자 목록은 탭이 아니라 사람 단위로 묶습니다.

<br>

### 5.4 셀 잠금은 서버가 지킵니다

지금 셀 잠금은 "이 범위를 잠갔어요"라고 알리고, 각 탭이 스스로 lock하는 방식입니다. 그래서 잠금이 전달되기 전 짧은 틈에 한 입력은 막지 못합니다. 탭 사이에서는 이 틈이 수 밀리초지만, 네트워크에서는 수백 밀리초로 늘어날 수 있습니다. 따라서 잠금을 서버가 관리해야 합니다.

- 서버에 잠금을 요청하고, 서버가 허락한 뒤에 AI 요청을 시작합니다.
- 잠금에는 유효 시간을 둡니다. 잠근 사람의 연결이 끊기면 자동으로 풀립니다. 지금 Web Locks가 하는 일을 서버가 대신합니다.
- 잠긴 셀을 바꾸는 변경이 오면 서버가 거부합니다.

다만 CRDT에서는 변경을 보낸 사람의 화면에 그 변경이 이미 반영되어 있습니다. 서버가 거부하면 그 화면을 다시 되돌려야해서 복잡해집니다. 그래서 지금처럼 화면에서 먼저 막고, 서버는 마지막으로 한 번 더 확인하는 구조가 현실적입니다.

<br>

### 5.5 어느 값이 남을지는 서버가 정합니다

앞에서 "같은 셀을 동시에 고치면 나중에 확정한 값이 남는다"고 했습니다. Yjs는 동시에 바뀐 값 중 무엇을 남길지 시간이 아니라 참여자 번호 순서로 정합니다. 탭 사이에서는 메시지가 거의 바로 도착해서 이 차이가 드러나지 않고 있습니다. 실제 네트워크 환경에서는 서로의 변경을 받기까지 시간이 길어지기 때문에, 먼저 확정한 값이 남을 수 있습니다.

AI 결과 적용에도 같은 문제가 있습니다. 지금은 현재 값 확인과 쓰기를 한 번에 처리하기 때문에, 그 사이에 다른 탭의 변경이 끼어들 수 없습니다. 하지만 네트워크로 전달되는 중인 변경까지는 확인할 수 없습니다.

따라서 AI 결과를 적용할 때는 서버에 "요청 때 값이 그대로인 셀만 바꿔 주세요"라고 요청하고, 서버가 확인과 쓰기를 한 번에 처리해야 합니다. "4. 아직 남은 한계"에서 언급한 "서버가 순서를 정해 줘야 한다"가 이 부분입니다.

<br>

### 5.6 오프라인에서 한 편집은 다시 연결될 때 병합합니다

오프라인에서 한 편집도 "동시에 한 편집"으로 처리됩니다. 그래서 몇 분 전에 입력한 값이 방금 다른 사람이 입력한 값을 덮어쓸 수 있습니다.

- 병합 결과를 그대로 반영할지, 다시 연결될 때 바뀐 셀을 알려 줄지, 오프라인 편집을 막을지 결정해야 합니다.
- 오프라인에서는 AI 결과 적용을 막아야 합니다. 현재 값을 신뢰할 수 없기 때문에 충돌 여부를 판단할 수 없습니다.
- 연결 상태(연결됨, 다시 연결 중)를 화면에 표시해야 합니다.

<br>

### 5.7 전송량을 줄입니다

지금은 입력 중인 글자는 한 글자마다, 선택 범위는 드래그하는 동안 계속 전송합니다. 탭 사이에서는 비용이 거의 없지만, 실제 네트워크 환경에서는 참여자가 많을수록 전송량이 크게 늘어납니다.

- 변경을 50~100ms 단위로 모아서 한 번에 전송합니다.
- 서버에서 한 시트의 최대 참여 인원과 전송 빈도를 제한합니다.

<br>

### 5.8 그 밖에 고려할 점

- 검토 중인 AI 제안을 서버에 저장하면, 새로고침 후에도 유지되고 다른 기기에서도 이어서 확인할 수 있습니다.
- 셀 주소, 값 길이, 변경 크기는 서버에서도 다시 검증합니다. 화면에서 막는 것만으로는 부족합니다.
- 배포 중에는 이전 버전과 새 버전의 클라이언트가 동시에 접속할 수 있습니다. 따라서 접속할 때 서로의 프로토콜 버전을 확인해야 합니다.
- 서버가 여러 대라면, 같은 시트의 사용자를 같은 서버로 연결하거나 서버끼리 변경을 공유하는 구조가 필요합니다.

<br>

### 5.9 두 단계로 나눠 적용합니다

1. 먼저 전송 방식을 바꾸고, 5.1~5.3(서버 저장, 연결 끊김 인식, 로그인)을 적용합니다. 여기까지 적용하면 다른 기기와 함께 편집할 수 있습니다.
2. 그다음 5.4~5.5(서버 잠금, 서버의 AI 적용 확인)을 적용합니다. 이를 통해 "4. 아직 남은 한계"에 적은 짧은 틈들을 없앨 수 있습니다.
